# Skiff — Decision Log

Decisions from the design grilling session on 2026-11-03. Format: decision, why, and rejected alternatives.

| # | Decision | Why | Rejected / deferred |
|---|---|---|---|
| D1 | Three runtime tiers: **static** (v1), **process** (v2), **container** (v2). One `Deployment` model with a `runtime` field. | Static costs ~0 per site, and designing tiers 2/3 now avoids a rewrite. | Docker-for-everything (daemon overhead, unnecessary for static). |
| D2 | **No server-side builds in v1.** Artifacts only. Git builds (v2) are a separate Builder that produces artifacts for the same pipeline. | Builds dominate resource use. One deploy path keeps everything downstream simple. | Building on the 4 GB VPS. |
| D3 | The v2 Builder runs on the **homelab**, as transient systemd units (memory/CPU/IO limits, one at a time, 10-minute timeout). | The homelab has 12 cores and 32 GB, and the edge stays responsive. | Builds on the VPS. |
| D4 | **Control plane + N node agents.** VPS = edge (ingress, TLS, control plane). Homelab = worker over **WireGuard** (dials out). Single-node mode is the same software. | No home port-forwarding, CGNAT-proof, home IP hidden, builds and heavy workloads on the homelab. | Two unrelated installs only; Cloudflare Tunnel for ingress. |
| D5 | An agent belongs to **exactly one** control plane. No federation. | Avoids split-brain. | Federated installs. |
| D6 | **Bun everywhere** (control plane, agent, CLI, v2 helper). Caddy is the only non-Bun component. | One language, shared contract types. | Go agent (~20–30 MB less RSS per node, accepted cost). |
| D7 | Caddy is driven **only via its admin API on a unix socket**. | Atomic changes, no reloads, and it closes the `localhost:2019` hijack hole. | Editing Caddyfiles; admin API on TCP. |
| D8 | **Cloudflare DNS, grey cloud.** Wildcard record + wildcard cert via DNS-01. | Instant subdomains, one cert, no rate limits, full control of TLS. | Orange-cloud proxy; per-site certs. |
| D9 | **Multi-tenant schema from day one:** Better Auth organizations + RBAC (`resource:action`), platform-admin vs org roles. Tokens are permission subsets. | Retrofitting ownership is painful. Lets agents get narrow permissions. | Single-user schema. |
| D10 | Sign-in with **passkeys + GitHub OAuth**, invite-only, 2FA for owners. | The dashboard can run code on the homelab. | Passwords; open signup. |
| D11 | **MCP over Streamable HTTP with OAuth 2.1** (Better Auth) for interactive clients, **API keys** as the headless fallback. Everything audited. | Works with Claude Code and Claude.ai; scoped and revocable. | API keys only. |
| D12 | Upload paths: **inline `deploy_files` (≤5 MB)** for chat agents and **presigned upload** for shell agents and CI. Git deferred. | Covers chat-only and shell agents without base64-ing tarballs through tool calls. | Git builds in v1. |
| D13 | **Every deployment gets an immutable preview URL**, plus a production pointer. `promote` defaults to true. Keep the last 10 deployments plus pinned. No named environments in v1 (column reserved). | Instant promote/rollback. RBAC can withhold `deployment:promote`. | Staging environments in v1. |
| D14 | Preview hostnames are `<slug>--<id>`, a single label. | A wildcard cert covers one level only. | Nested `<id>.<slug>.domain`. |
| D15 | Built-in observability: **SQLite for state, DuckDB for telemetry**, cold Parquet archive. | Lightweight, fast aggregations, cheap long retention. | Prometheus/Loki/Grafana stack (~0.5–1 GB). |
| D16 | **OTel-conformant** (OTLP and semantic conventions), our own OTLP receiver, **export only** (`/metrics` + OTLP out). Import is designed, not built. | Interoperable without rebuilding Grafana. | Running the OTel Collector; importing from Prometheus in v1. |
| D17 | **Deployment = release + config snapshot.** Rollback restores code and config. | Reproducible previews; avoids "rollback didn't fix it". | Live config separate from deployments. |
| D18 | Secrets: envelope encryption, master key in `systemd-creds` (TPM2 where available), write-only via API/MCP, env vars by default with a file opt-in. | Strong at-rest protection with framework compatibility. | Plaintext config; readable secrets. |
| D19 | **A separate content domain is supported and recommended.** A single shared domain is allowed with mandatory hardening and a persistent warning. | Deployed (AI-generated) content must not be same-site with the dashboard. | Forcing two domains; shared domain without hardening. |
| D20 | Access modes `public / password / platform`. Defaults: prod public, previews platform. Enforced by `forward_auth` to the **local agent** with stateless HMAC host-only cookies. | No per-request DB or network cost; platform cookies never touch the content domain. | `forward_auth` to the control plane; parent-domain cookies. |
| D21 | **Share links** with expiry, visitor/redemption caps, session TTL, email binding, and revocation pushed to agents. A visit is a redemption. | Scriptable sharing without stateful checks on every request. | Counting page loads. |
| D22 | Email via the **SES SMTP** (generic SMTP transport). Alerts via email + webhook. The installer creates DKIM/SPF/DMARC via the Cloudflare API. | The user already uses SES; mail from a VPS IP delivers poorly. | Self-hosted mail; Resend. |
| D23 | **Desired-state reconciliation.** Agents pull, converge, and cache state on disk. | The control plane can be down without affecting live sites. | Imperative push commands. |
| D24 | **The VPS is an accepted single point of failure in v1**, mitigated by restore in under 15 minutes and a monthly restore drill. | Real ingress failover adds many moving parts. | Cloudflare Tunnel backup ingress + DNS failover (future). |
| D25 | **R2 is the canonical object store in v1** (artifacts, Litestream, Parquet) behind an `ObjectStore` interface. Presigned uploads go direct to R2. Recovery kit (`age`) for the master key. | Offsite by default, no egress fees, saves VPS disk and bandwidth. | Local fs, Garage/MinIO, multi-target (all v2). |
| D26 | Least privilege: control plane and agent unprivileged. **v1 needs no root.** v2 helper renders units from validated specs only. | Small blast radius. | Agent as root. |
| D27 | **Debian 13 on both nodes. The homelab node is a VM on Unraid.** `RuntimeDriver` interface kept, with a `docker` driver as an optional v2 item. | The Docker socket on Unraid is root over the NAS array. A VM gives a hypervisor boundary. | Docker on Unraid with a socket proxy. |
| D28 | **Personal now, product-grade engineering**: signed releases, semver, forward-only migrations with snapshots, installer from a clean VM, browser setup wizard, self-update with automatic rollback. | Keeps the open-source option open at little extra cost. | Throwaway personal tooling; full product polish now. |
| D29 | The MCP surface is intent-shaped (`deploy_site` one-shot plus granular tools). Default consent = deployer. Delete is opt-in, confirmed via **elicitation**, soft-deleted for 7 days. | Agents succeed in one call; humans gate destruction. | Low-level-only tools; agents able to delete freely. |
| D30 | Static config via **Netlify-style `_redirects` / `_headers`** plus optional `skiff.json`, compiled into the deployment snapshot. Precompress at deploy time. Immutable caching for hashed assets. | LLMs already know these formats; no per-request cost. | A platform-only config format. |
| D31 | **Custom domains deferred to v2** (design kept: TXT verify, on-demand TLS + `ask`, Cloudflare auto-records). | Scope. | v1 custom domains. |
| D32 | Slugs: 3–40 chars, `[a-z0-9-]`, **no `--`**, globally unique, reserved list, collision → suggestions, rename → 30-day 301. Per-org quotas in the schema. | Shared namespace across orgs; unambiguous preview URLs. | Auto-suffixing (`-2`). |
| D33 | Product name: **Skiff**. CLI npm package: **`skif`** (unscoped, available on npm). Installing it provides **both `skif` and `skiff` commands** (two `bin` entries, same entrypoint), so either spelling works. | Small, fast, light boat that ships things. | Tender, Burrow, Mote, Tern. |
| D34 | Deployment domains: platform **`kieran.dev`**, content **`kierancloud.dev`**; control plane at **`control.kieran.dev`**, sites at `<slug>.kierancloud.dev`. Edge is the `private-cloud` VPS (`178.104.255.136`), Caddy 2.11.7 + `caddy-dns/cloudflare`, admin only on `unix//var/lib/caddy/admin.sock`. Cloudflare records are grey-cloud; TLS is DNS-01 wildcard. | Two-domain mode (D19) keeps platform auth cookies off deployed content. Grey cloud + DNS-01 means one wildcard cert and no per-site DNS or TLS work. | Shared domain (samesite exposure); orange-cloud proxy (couples the setup to Cloudflare SSL mode). |
| D34 | **CIMD + DCR** for MCP client identity: CIMD (MCP 2026-07-28) by default, DCR kept for older clients behind `SKIFF_MCP_ALLOW_DCR`. CIMD fetches go through Better Auth's SSRF-safe pinned transport. | Spec moved to CIMD, but current clients still register via DCR. | CIMD-only (breaks older clients); DCR-only (deprecated). |
| D35 | Destructive MCP actions are confirmed via **multi-round-trip input**, bound to the target. 2025-era clients get a dashboard hand-off. Missing permissions trigger **OAuth scope step-up**, not a hard failure. | Stateless servers can't push elicitation on the 2026-07-28 protocol; step-up keeps "grant delete only when needed" possible. | Server-pushed elicitation (needs sessions); always-fail on missing scope. |
| D36 | SvelteKit's CSRF check is disabled and replaced by Skiff's **stricter** Origin policy (every mutation same-origin, exact allowlist of cookieless OAuth/MCP endpoints). | Kit's check runs before hooks, is all-or-nothing, and blocks the OAuth token endpoint. | Kit's default check (breaks OAuth); no CSRF protection. |
| D37 | Control plane runs on **adapter-bun over a unix socket** behind Caddy (`SOCKET_PATH`, `PROTOCOL_HEADER`, `HOST_HEADER`). | No TCP port to expose or misconfigure, and it was verified end to end in the spike. | TCP on localhost. |
| D38 | CLI settings and credentials share `~/.config/skiff/config.json` (0600): `url`, `contentDomain`, `token`. `skif config` manages them; `logout` removes only the token. `SKIFF_URL`/`SKIFF_TOKEN`/`SKIFF_CONTENT_DOMAIN` override the file. | The control URL and site domain are not secrets and should not be retyped after every logout, while CI still needs env-only operation. | Separate settings/credential files; wiping the whole config on logout; flags only. |
| D39 | **Browser-first `skif login`**: the dashboard approves the CLI and redirects a one-time **PKCE-bound code** to a loopback listener; the CLI exchanges it for a freshly minted API key. The code is stored hashed, expires in five minutes, and is single-use. `--token` keeps API-key login for CI and headless use. | The REST API authenticates API keys, so the browser step authenticates the human while the CLI keeps the existing long-lived credential. A bespoke approval avoids OAuth client registration, audience-bound MCP tokens and refresh-token storage. | Reusing MCP OAuth (audience-bound to `/mcp`, short-lived); putting the API key in the redirect URL; device-code flow (more server and UI surface for the same result). |
| D40 | The **`@skiffy/skiff` npm package (commands `skif` and `skiff`) ships a single bundled `dist/skif.js` that runs on Node 20+ or Bun**. The CLI is still developed and tested with Bun (D6) but uses only `node:` APIs at runtime, and has no runtime dependencies. MIT licensed. It is **versioned independently** of the platform and released from a manual **Release CLI** workflow (`workflow_dispatch`): pick a bump or version, and it commits the bump to `main`, tags `cli-v<version>`, publishes with npm provenance (prereleases to the `next` dist-tag) and creates a non-latest GitHub release. Re-running with the same version resumes a partial release. | Most people running `npx @skiffy/skiff` have Node but not Bun, and a self-contained bundle installs instantly. CLI fixes ship without cutting a platform release, and a button needs no local tooling or release branch to keep in sync. | Bun-only `bin` (needs Bun installed); unscoped `skif` (npm rejects it as too similar to `swig`/`sift`); scoped `@skiff/cli` (the `@skiff` scope is already taken on npm); publishing on platform `v*` tags; a `cli-release` branch that publishes on push. |
| D41 | **The edge node can run apps too.** Tier-2/3 workloads can be placed on any node, the edge included; the edge is not static-only. Every node runs apps in `skiff-workloads.slice` with a per-node memory budget (edge default 1 GiB) and lower CPU weight than the platform services, with deploy-time admission against that budget. `auto` resolves at deploy time: static → edge, apps → a worker with budget, else the edge. Builds stay on the homelab (D3). Refines D4. | Apps on the edge survive a homelab outage, skip the WireGuard hop, and single-node installs need it anyway. The slice and admission keep a runaway app from taking down ingress and the control plane on a 4 GB VPS. | Homelab-only apps (edge static-only); edge apps without a shared budget (one app can starve Caddy and the control plane); builds on the edge. |
| D42 | **Admission is a stored budget, not a guess.** Each node carries `slice_memory_mb` (edge default 1024) and the control plane sums `pending/starting/running` workload reservations before accepting a deploy. `auto` prefers the worker with the most free budget, then the edge. The node's budget is sent in desired state and the agent applies it to `skiff-workloads.slice` before starting units. | Admission must match the kernel limit even if an operator changes the budget; duplicating the number in agent env would drift. | Admission at runtime only (a deploy could be accepted and then OOM); a global budget (one noisy app starves a node). |
| D43 | **Privileged helper with fixed verbs.** The agent never runs as root; `skiff-helper` renders unit/Quadlet files from validated fields and exposes only slice/workload create, start, status and remove on a unix socket restricted to `root:skiff` (`0660`). Secret values are fetched just-in-time from the control plane, written `0400` under `/run/skiff-workloads/<id>/`, and never enter desired state or its disk cache. | Closes the privilege gap without giving the agent a shell; a compromised agent can only manage workloads it was already given. | Agent as root (D26 rejects it); a generic "run this command" helper verb (a shell in disguise). |
| D44 | **Named environments are per project and single-label.** `production` is built in and keeps `<slug>.<contentDomain>`; every other environment is `<slug>--<env>.<contentDomain>` so the existing wildcard certificate covers it. Non-production deploys and promotions never touch `projects.production_deployment_id`. v2 runs **one workload per project** (only the latest deployment is active; a production promote or rollback re-points it); per-deployment preview runtimes are deferred. | Fits D14's one-level wildcard constraint and keeps production promotion history/compatibility intact. | `env.<slug>.<domain>` (needs a second wildcard); running a unit per preview (resource blow-up on a 4 GB edge). |
| D45 | **Builds run only on nodes flagged `can_build`, one at a time.** The Builder claims a queued job with its node token, clones a public HTTPS repo (optional global `SKIFF_GIT_TOKEN`), runs the build in a transient `systemd-run` unit (`MemoryMax=2G`, `CPUQuota=200%`, 10-minute wall clock), uploads the zip, and the control plane finalizes it through the normal release/deploy path. **GitHub webhooks require a per-project secret**; unsigned deliveries are rejected. | Keeps user code off the control plane and the edge, bounds build cost, and prevents anyone from triggering builds on a public repo. | Building on the edge (D3 rejects it); unsigned webhooks for convenience; per-project private-repo credentials in v2 (schema work deferred). |
| D46 | **CLI profiles live in the one config file.** `~/.config/skiff/config.json` holds `profiles.<name>.{url,contentDomain,token}` plus `activeProfile`. Selection is `--profile` > `$SKIFF_PROFILE` > the active profile > the only profile when exactly one exists; with several and no active, commands refuse to guess and list them. Legacy single-profile files are read as profile `default` and upgraded on the next write. `skif profile list\|add\|use\|remove\|show\|current` manages them; `logout --all` removes all profiles. Refines D38. | One machine routinely targets production, staging and a local dev server. Named profiles keep the non-secret URL/domain next to the key, avoid env-var juggling, and still let CI run statelessly with `SKIFF_URL`/`SKIFF_TOKEN` (no profile required). | A separate config directory per deployment (has to be wired into every shell/launcher); per-project profiles (profiles belong to deployments, not projects); requiring `--profile` once more than one exists (breaks the common single-deployment case). |
| D47 | **Any node can be a Builder; the role is a dashboard toggle.** Amends D3/D45: the edge is no longer excluded. Every node runs `skiff-builder.service` (`skiff-agent builder`, from the agent binary already on the node, using its node token) and idles until a platform admin sets `can_build` from **Nodes → Edit node** or `PATCH /api/v1/nodes/:id`. The daemon is root only to start each build with `systemd-run` as the unprivileged `skiff-build` user, in a sandbox that can write only its checkout and cannot read `/etc/skiff`, `/var/lib/skiff` or `/run/skiff`. Builds never see the node token. The same edit surface changes a node's name, address and workload-slice memory/CPU weight; the memory budget cannot drop below current reservations (D42). | Small fleets often have only the edge, or several equivalent workers. Making builds depend on a separately installed homelab daemon left the role toggle doing nothing on most nodes. | A separate `skiff-builder` binary and installer path; running builds inside the agent's 192 MB sandbox; a build verb on `skiff-helper` (more privileged surface for the same result); keeping edge builds forbidden. |
| D48 | **Node storage locations are a dashboard setting, applied by a root oneshot on the node.** Each node stores `storage_data_dir` (agent state and release cache, which Caddy serves from) and `storage_build_dir` (Builder scratch); `null` keeps the install defaults (`/var/lib/skiff/agent`, `/var/lib/skiff-builder`). They reach the node in desired state. The agent cannot move its own data (its sandbox only writes the current paths), so it drops `/run/skiff/storage.request`, and `skiff-storage.path` runs `skiff-agent storage apply` as root. That command ignores the request's contents, fetches the paths from `GET /api/agent/storage` with the node token, and re-checks them against the shared rules in `@skiff/contracts` (absolute, normalized, not a system tree, other Skiff state, `/home` or a bare mount root). A data move stops the agent, copies with `cp -a`, re-points site links, sets `SKIFF_DATA_DIR` in agent.env, adds a `ReadWritePaths=` drop-in, starts the agent, and deletes the old copy only once the agent has stayed up. Any failure rolls back. Moves wait for running builds. The result is written to `/etc/skiff/storage.json` and relayed in heartbeats. Control-plane data (`/var/lib/skiff/data`) is out of scope. | Operators outgrow the root partition after install; moving by hand means editing units, env files and symlinks consistently on every node. | Letting the agent move data itself (needs a writable `/`); trusting paths written by the agent; mount/bind-mount instructions only; copying and keeping the old copy forever. |
| D49 | **Mass actions and prune share one Operation primitive**: plan → (review) → apply, per-item status persisted as it runs, resumable after a restart, SSE progress, one `applying` run per org per kind. Actions are registered `ActionDefinition`s whose metadata lives in `@skiff/contracts`, so the dashboard, CLI and MCP list them without new plumbing (docs/OPERATIONS.md). | One place for progress, audit, limits and cancel; a future mass action is one definition. | A `/projects/bulk-*` endpoint per action; client-side loops over single-item endpoints (no progress, no resumption, no grouped audit). |
| D50 | **Explicit targets only.** Bulk operations take a list of slugs/ids (≤100, ≤25 over MCP). Filters (`--match`, not deployed, older than) are resolved by the client into that list before planning. | The human confirms exactly what is acted on; a project created after the confirmation can't match a filter and be deleted. | Server-side filter selectors for destructive actions. |
| D51 | **Per-item success.** Each item is idempotent, runs in its own transaction with its own audit row (`audit_log.operation_id`), and is re-verified at apply time; `partial` is a valid outcome. | Items have side effects outside SQLite (Cloudflare, agents, object store) that can't be rolled back; one failure must not block 99 good deletes. | All-or-nothing transactions. |
| D52 | **Prune removes only unreferenced data, always plan-then-apply**, with a 24 h grace window and a 1 h plan expiry. Org scope needs `project:delete`; platform scope (incl. stored objects, which are content-addressed and shared across orgs) needs a platform admin session or API key. Cheap, certain cleanup (trash cascade, old deleted deployments, snapshot GC) stays automatic in the maintenance sweep. | "Not connected" must be seen before it runs; the grace window protects in-flight uploads and deploys. | Pruning "unused" but owned resources; one-shot prune; prune over MCP. |
| D53 | MCP gets **`delete_projects`** (≤25, one elicitation listing every slug, bound to the planned operation id), **`restore_projects`** and `get_operation`. **No purge and no prune over MCP**; 2025-era clients get a dashboard link with the selection. | Keeps D29: agents do reversible things with confirmation, humans gate irreversible ones. | Bulk purge for agents; no bulk tools at all. |
| D54 | The dashboard has a **Trash** view (bulk restore / delete permanently) and bulk delete offers **Undo**; restore re-checks the project quota. Typed confirmation for ≥5 items, any live site, and every permanent delete. | Mass delete needs a visible, fast way back. | Restore through the API only. |
| D55 | **Managed databases are org resources run as tier-3 containers** ([DATABASES.md](./DATABASES.md)). A `databases` row (not a project) is sent to its node as a container `WorkloadDesired` with a `database` field; it sits in `skiff-workloads.slice` and counts toward the node's admission budget (D42). Placement is resolved once at create time and never moves (D41). | Reuses the helper, slice, heartbeat and log paths already hardened for apps; no second runtime. | Databases as a project runtime (they have no releases, routes or deployments); a shared Postgres cluster with one database per tenant (one noisy tenant affects all, no per-database limits); a host-installed Postgres (root package management on every node). |
| D56 | **Same-node attachments only in v1.** Databases publish on `127.0.0.1` and the `skiff-workloads` Podman network, never on a public or WireGuard address. A project with attachments is placed on the database's node at deploy time; process apps get `127.0.0.1:<hostPort>`, container apps get `db-<id>:5432`. Connection values (`<PREFIX>_URL` etc.) are injected at activation only and the activation version covers attachments. | The only node address we store (`public_address`) is not guaranteed to be private, and binding a database to the edge's public IP would expose it. Same-node is safe and covers single-node installs. | Binding to `public_address` (may be public); a TCP proxy through the agent (more moving parts); injecting the URL into the project spec (would put a password in desired state). |
| D57 | **Database stats go to DuckDB through the existing telemetry batch.** The agent samples `pg_stat_database`/`pg_stat_activity` every minute as a `skiff_monitor` role (`pg_monitor` only, bootstrapped by the agent with the owner credentials, held in memory only) and sends gauges plus counter deltas; `db_metrics_1m` rolls up into `db_metrics_1h` with traffic's retention. The latest top-50 table snapshot lives in SQLite. | One ingest path, one retention policy, one store for every time series (D15); the control plane never needs network reach to a database. | Querying databases from the control plane (no route to the node's loopback); a Prometheus postgres_exporter per database (an extra process per DB and a scrape stack D15 rejected). |
| D58 | **Database credentials are sealed with the org key and revealed only to humans.** `GET /databases/:name/credentials` needs `database:credentials` (never pre-ticked for agents) and is audited. MCP never returns them; agents get the URL injected into apps instead. | Agents don't need the password to build working apps; keeps D18's write-only spirit for anything an agent can see. | Readable credentials over MCP; storing them as ordinary org secrets (they'd show up in, and could be deleted from, the secrets list). |
| D59 | **Database delete is soft for 7 days and refused while projects are attached.** The container stops but the data dir stays, so restore is lossless. Purge goes through desired state (`databasePurges`) to a fixed helper verb that removes only `<stateDir>/<id>`, then the row is deleted on the agent's report. | Data loss must be reversible like project deletes (D29); the helper keeps fixed verbs only (D43). | Hard delete; deleting the data dir whenever a workload leaves desired state (a transient desired-state bug would wipe data). |
| D60 | **No Drizzle Studio. The SQL console will be an open-source admin UI (pgweb or Adminer) run on demand** as a short-lived container on the database's node, behind `platform` access with `database:console`, audited and idle-stopped. The dashboard's own database view stays small and native (status, connection, attachments, charts, tables). | Drizzle Studio's UI is hosted by Drizzle and not embeddable without a commercial agreement; Drizzle Gateway needs Drizzle's licence server. A full table editor is its own product. The control plane can't reach node-local databases anyway. | Embedding Drizzle Studio/Gateway; building a table editor from scratch. |
| D61 | **Engines are a registry, and the helper derives the image itself.** The wire carries only `engine` + `version` (`postgres` 16/17 in v1); the helper maps them to a fixed image, user, mounts and port. | The helper must not run an arbitrary image with database privileges (chowned data dir); a registry keeps MySQL/Valkey a data change, not a rewrite. | Sending the image from the control plane; hard-coding Postgres across services. |
| D62 | **Managed object storage is org resources run as tier-3 containers** ([OBJECT-STORAGE.md](./OBJECT-STORAGE.md), S1). A `storage_instances` row (not a project) is a single RustFS server on one node, in `skiff-workloads.slice`, admitted against the node budget (D42). Namespace `storage` already means node storage (D48), so wire fields are `objectStorage`/`storageRoutes`/`storagePurges`. | Reuses the database runtime profile, helper, heartbeat and log paths; per-instance limits mean one noisy tenant cannot starve the fleet. | A shared S3 cluster with a bucket per tenant (same reasoning as D55); storage instances as projects (no releases, routes or deployments). |
| D63 | **RustFS's built-in console is off** (S2); Skiff is the only bucket/key management surface. | Keeping a second admin UI would make Skiff's desired state diverge from reality; the console also needs its own exposure and auth story. | Exposing the console; per-instance console credentials. |
| D64 | **S3 exposure is a per-instance toggle: private by default, public via a dedicated route** on `<name>--s3.<contentDomain>` (S3). The route has no `forward_auth`, no site config and byte-for-byte proxying with `Host` preserved both hops, `flush_interval -1` and long timeouts; path-style only. `public_host` has a global unique index and the environment slugs `s3`/`console` are reserved. | S3 clients carry no cookies, so the SigV4 signature is the access control; proxying unchanged keeps presigned URLs and multipart uploads working. One wildcard level fits D14/D44. | Virtual-hosted-style buckets (needs a second wildcard); `forward_auth` in front of S3 (clients can't authenticate); terminating S3 TLS inside the container. |
| D65 | **Buckets and scoped keys are desired state, converged by the agent over loopback** (S4). The instance's workload lists buckets and `SKF*` users; the agent creates buckets, sets `public-read` policies, deletes only through an explicit `deleteBuckets` entry, and creates IAM users limited to their grants. The root key is fetched at activation and held in agent memory only; attachment secrets never reach the helper or disk. | A transient desired-state bug must never wipe data (as D59); apps get scoped keys instead of the root key, and no credential is stored on the node. | Deleting buckets that disappear from desired state; one shared non-root key per instance (no per-app grants); writing the root key into the unit/env file. |
| D66 | **Same-node attachments for private instances; public instances work from any node** (S5). Attach injects `<P>_ENDPOINT_URL`, `<P>_ACCESS_KEY_ID`, `<P>_SECRET_ACCESS_KEY`, `<P>_REGION=us-east-1`, `<P>_FORCE_PATH_STYLE=true`, `<P>_PUBLIC_ENDPOINT_URL` (public only) and `<P>_BUCKET` (single grant) at activation; the prefix defaults to `S3` and `AWS` matches the AWS SDKs. | Private S3 must not bind a public address (D56); a public instance's TLS-authenticated S3 is the first safe cross-node managed resource. Activation-time injection keeps secrets out of desired state (D18/D43). | Binding private S3 to `public_address`; putting credentials in the project spec; requiring a redeploy for attach/detach. |
| D67 | **The root key is sealed with the org key and revealed only to humans** (S6): `GET /storage/:name/credentials` needs `storage:credentials` and every read is audited; MCP never returns keys.
