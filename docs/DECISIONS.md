# Skiff — Decision Log

The decisions in force. Started at the design grilling session on 2026-11-03 and kept current: a
decision that no longer applies is removed rather than left with a "superseded" note, and a row
that was amended states what is true now. IDs are never renumbered or reused, because code and
docs cite them; retired IDs are listed at the end. Format: decision, why, and rejected alternatives.

| # | Decision | Why | Rejected / deferred |
|---|---|---|---|
| D1 | Three runtime tiers: **static**, **process** and **container**. One `Deployment` model with a `runtime` field. | Static costs ~0 per site; process and container share placement, admission, units and logs. | Docker-for-everything (daemon overhead, unnecessary for static). |
| D2 | **Builds produce artifacts; the control plane never builds.** Uploads and git builds (D45, D47) feed the same release → deployment pipeline. | Builds dominate resource use. One deploy path keeps everything downstream simple. | Building inside the control plane; a separate deploy path for git builds. |
| D4 | **Control plane + N node agents over a private WireGuard overlay.** Nodes dial out, so no node needs inbound ports; single-node mode is the same software over a unix socket. Which nodes take ingress, control, compute, data and build work is node configuration ([CLUSTERING.md](./CLUSTERING.md)). | No home port-forwarding, CGNAT-proof, home IP hidden; heavy workloads go wherever the hardware is. | Several unrelated installs. |
| D5 | An agent belongs to **exactly one** install, and an install has **one active control plane** at a time; warm standbys belong to the same install (D107). No federation. | Avoids split-brain. | Federated installs. |
| D6 | **Bun everywhere** (control plane, agent, CLI, helper). Caddy is the only non-Bun component. | One language, shared contract types. | Go agent (~20–30 MB less RSS per node, accepted cost). |
| D7 | Caddy is driven **only via its admin API on a unix socket**. | Atomic changes, no reloads, and it closes the `localhost:2019` hijack hole. | Editing Caddyfiles; admin API on TCP. |
| D8 | **Cloudflare DNS with a wildcard record and a wildcard certificate via DNS-01.** Records may be DNS-only or proxied (Full (strict)); new sites need no DNS calls. How clients reach several ingress nodes is an ingress driver (D107). | Instant subdomains, one certificate, no per-site DNS or TLS work. | Per-site certificates and records. |
| D9 | **Multi-tenant schema from day one:** Better Auth organizations + RBAC (`resource:action`), platform-admin vs org roles. Tokens are permission subsets. | Retrofitting ownership is painful. Lets agents get narrow permissions. | Single-user schema. |
| D10 | Sign-in with **passkeys, GitHub OAuth, magic links and email + password** (D103), invite-only. Owners prove a second factor every session. | The dashboard can run code on every node. | Open sign-up; single-factor owners. |
| D11 | **MCP over Streamable HTTP with OAuth 2.1** (Better Auth) for interactive clients, **API keys** as the headless fallback. Everything audited. | Works with Claude Code and Claude.ai; scoped and revocable. | API keys only. |
| D12 | Upload paths: **inline `deploy_files` (≤5 MB)** for chat agents and **presigned upload** for shell agents and CI; git builds feed the same pipeline (D2). | Covers chat-only and shell agents without base64-ing tarballs through tool calls. | A single upload path for every client. |
| D13 | **Every deployment gets an immutable preview URL**, plus a production pointer. `promote` defaults to true. Keep the last 10 deployments plus pinned. Named environments are D44. | Instant promote/rollback. RBAC can withhold `deployment:promote`. | Mutable previews. |
| D14 | Preview hostnames are `<slug>--<id>`, a single label. | A wildcard cert covers one level only. | Nested `<id>.<slug>.domain`. |
| D15 | **SQLite holds platform state**; telemetry has its own store (D101) with a cold Parquet archive in the object store. Observability is built in rather than a bundled Prometheus/Loki/Grafana stack. | Lightweight, and one file to stream with Litestream. | Prometheus/Loki/Grafana stack (~0.5–1 GB). |
| D16 | **OTel-conformant** (OTLP and semantic conventions), our own OTLP receiver, `/metrics` and OTLP export. Importing external sources is not built yet. | Interoperable without rebuilding Grafana. | Running the OTel Collector. |
| D17 | **Deployment = release + config snapshot.** Rollback restores code and config. | Reproducible previews; avoids "rollback didn't fix it". | Live config separate from deployments. |
| D18 | Secrets: envelope encryption, master key in `systemd-creds` (TPM2 where available), write-only via API/MCP, env vars by default with a file opt-in. | Strong at-rest protection with framework compatibility. | Plaintext config; readable secrets. |
| D19 | **A separate content domain is supported and recommended.** A single shared domain is allowed with mandatory hardening and a persistent warning. | Deployed (AI-generated) content must not be same-site with the dashboard. | Forcing two domains; shared domain without hardening. |
| D20 | Access modes `public / password / platform`. Defaults: prod public, previews platform. Enforced by `forward_auth` to the **local agent** with stateless HMAC host-only cookies. | No per-request DB or network cost; platform cookies never touch the content domain. | `forward_auth` to the control plane; parent-domain cookies. |
| D21 | **Share links** with expiry, visitor/redemption caps, session TTL, email binding, and revocation pushed to agents. A visit is a redemption. | Scriptable sharing without stateful checks on every request. | Counting page loads. |
| D22 | **Platform** email (sign-in links, invites, alerts) via the **SES SMTP** (generic SMTP transport); tenant email is Skiff's own MTA (D114). Alerts via email + webhook, plus chat channels with each service's native payload (Discord, Slack, Telegram, ntfy), configured from env keys like the rest of the platform settings. The installer creates DKIM/SPF/DMARC via the Cloudflare API. | The user already uses SES; mail from a VPS IP delivers poorly. | Self-hosted mail; Resend. |
| D23 | **Desired-state reconciliation.** Agents pull, converge, and cache state on disk. | The control plane can be down without affecting live sites. | Imperative push commands. |
| D25 | **Platform artifacts, Litestream and the Parquet archive live behind an `ObjectStore` interface** (`local`, or any S3-compatible endpoint; R2 is the default). Presigned uploads go direct to the store. Recovery kit (`age`) for the master key. | Offsite by default with R2, no egress fees, saves node disk and bandwidth; the interface keeps local-only installs possible. | Hard-coding one provider. |
| D26 | Least privilege: the control plane and agent run unprivileged. Root work happens only in `skiff-helper`'s fixed verbs (D43) and root oneshots driven by request files (D48). | Small blast radius. | Agent as root. |
| D27 | **Nodes run Debian 13 or Ubuntu LTS. A homelab node on Unraid is a VM**, not a Docker container. The `RuntimeDriver` interface keeps an optional `docker` driver possible. | The Docker socket on Unraid is root over the NAS array. A VM gives a hypervisor boundary. | Docker on Unraid with a socket proxy. |
| D28 | **Personal now, product-grade engineering**: signed releases, semver, forward-only migrations with snapshots, installer from a clean VM, browser setup wizard, self-update with automatic rollback. | Keeps the open-source option open at little extra cost. | Throwaway personal tooling; full product polish now. |
| D29 | The MCP surface is intent-shaped (`deploy_site` one-shot plus granular tools). Default consent = deployer. Delete is opt-in, confirmed via **elicitation**, soft-deleted for 7 days. | Agents succeed in one call; humans gate destruction. | Low-level-only tools; agents able to delete freely. |
| D30 | Static config via **Netlify-style `_redirects` / `_headers`** plus optional `skiff.json`, compiled into the deployment snapshot. Precompress at deploy time. Immutable caching for hashed assets. | LLMs already know these formats; no per-request cost. | A platform-only config format. |
| D31 | **Custom domains** are verified with a `_skiff` TXT record and get certificates issued as soon as they are verified, not on demand. When the zone is in the connected Cloudflare account, Skiff creates the records. | On-demand issuance never starts behind the Cloudflare proxy (it refuses to forward to an origin without a certificate), and the verified list is already the authorisation. | On-demand TLS with an `ask` endpoint. |
| D32 | Slugs: 3–40 chars, `[a-z0-9-]`, **no `--`**, globally unique, reserved list, collision → suggestions, rename → 30-day 301. Per-org quotas in the schema. | Shared namespace across orgs; unambiguous preview URLs. | Auto-suffixing (`-2`). |
| D33 | Product name: **Skiff**. The CLI installs **both `skif` and `skiff` commands** (two `bin` entries, same entrypoint) from the npm package in D40, so either spelling works. | Small, fast, light boat that ships things. | Tender, Burrow, Mote, Tern. |
| D34 | **CIMD + DCR** for MCP client identity: CIMD (MCP 2026-07-28) by default, DCR kept for older clients behind `SKIFF_MCP_ALLOW_DCR`. CIMD fetches go through Better Auth's SSRF-safe pinned transport. | Spec moved to CIMD, but current clients still register via DCR. | CIMD-only (breaks older clients); DCR-only (deprecated). |
| D35 | Destructive MCP actions are confirmed via **multi-round-trip input**, bound to the target. 2025-era clients get a dashboard hand-off. Missing permissions trigger **OAuth scope step-up**, not a hard failure. | Stateless servers can't push elicitation on the 2026-07-28 protocol; step-up keeps "grant delete only when needed" possible. | Server-pushed elicitation (needs sessions); always-fail on missing scope. |
| D36 | SvelteKit's CSRF check is disabled and replaced by Skiff's **stricter** Origin policy (every mutation same-origin, exact allowlist of cookieless OAuth/MCP endpoints). | Kit's check runs before hooks, is all-or-nothing, and blocks the OAuth token endpoint. | Kit's default check (breaks OAuth); no CSRF protection. |
| D37 | Control plane runs on **adapter-bun over a unix socket** behind Caddy (`SOCKET_PATH`, `PROTOCOL_HEADER`, `HOST_HEADER`). | No TCP port to expose or misconfigure, and it was verified end to end in the spike. | TCP on localhost. |
| D39 | **Browser-first `skif login`**: the dashboard approves the CLI and redirects a one-time **PKCE-bound code** to a loopback listener; the CLI exchanges it for a freshly minted API key. The code is stored hashed, expires in five minutes, and is single-use. `--token` keeps API-key login for CI and headless use. | The REST API authenticates API keys, so the browser step authenticates the human while the CLI keeps the existing long-lived credential. A bespoke approval avoids OAuth client registration, audience-bound MCP tokens and refresh-token storage. | Reusing MCP OAuth (audience-bound to `/mcp`, short-lived); putting the API key in the redirect URL; device-code flow (more server and UI surface for the same result). |
| D40 | The **`@skiffy/skiff` npm package (commands `skif` and `skiff`) ships a single bundled `dist/skif.js` that runs on Node 20+ or Bun**. The CLI is still developed and tested with Bun (D6) but uses only `node:` APIs at runtime, and has no runtime dependencies. MIT licensed. It is **versioned independently** of the platform and released from a manual **Release CLI** workflow (`workflow_dispatch`): pick a bump or version, and it commits the bump to `main`, tags `cli-v<version>`, publishes with npm provenance (prereleases to the `next` dist-tag) and creates a non-latest GitHub release. Re-running with the same version resumes a partial release. | Most people running `npx @skiffy/skiff` have Node but not Bun, and a self-contained bundle installs instantly. CLI fixes ship without cutting a platform release, and a button needs no local tooling or release branch to keep in sync. | Bun-only `bin` (needs Bun installed); unscoped `skif` (npm rejects it as too similar to `swig`/`sift`); scoped `@skiff/cli` (the `@skiff` scope is already taken on npm); publishing on platform `v*` tags; a `cli-release` branch that publishes on push. |
| D41 | **Any node can run any tier, the edge included.** Every node runs apps in `skiff-workloads.slice` with a per-node memory budget (edge default 1 GiB) and lower CPU weight than the platform services, with deploy-time admission against that budget. `auto` resolves at deploy time: static → ingress, apps → a worker with budget, else the edge. A running workload moves only through an explicit move (D97) or a failover its HA policy opts into (D107). Refines D4. | Apps on the edge survive a homelab outage, skip the WireGuard hop, and single-node installs need it anyway. The slice and admission keep a runaway app from taking down ingress and the control plane on a 4 GB VPS. | A static-only edge; edge apps without a shared budget (one app can starve Caddy and the control plane). |
| D42 | **Admission is a stored budget, not a guess.** Each node carries `slice_memory_mb` (edge default 1024) and the control plane sums `pending/starting/running` workload reservations before accepting a deploy. `auto` prefers the worker with the most free budget, then the edge. The node's budget is sent in desired state and the agent applies it to `skiff-workloads.slice` before starting units. | Admission must match the kernel limit even if an operator changes the budget; duplicating the number in agent env would drift. | Admission at runtime only (a deploy could be accepted and then OOM); a global budget (one noisy app starves a node). |
| D43 | **Privileged helper with fixed verbs.** The agent never runs as root; `skiff-helper` renders unit/Quadlet files from validated fields and exposes only slice/workload create, start, status and remove on a unix socket restricted to `root:skiff` (`0660`). Secret values are fetched just-in-time from the control plane, written `0400` under `/run/skiff-workloads/<id>/`, and never enter desired state or its disk cache. The one bounded exception is the container console (D127): a fixed shell inside a project's own container, never on the host. | Closes the privilege gap without giving the agent a shell; a compromised agent can only manage workloads it was already given. | Agent as root (D26 rejects it); a generic "run this command" helper verb (a shell in disguise). |
| D44 | **Named environments are per project and single-label.** `production` is built in and keeps `<slug>.<contentDomain>`; every other environment is `<slug>--<env>.<contentDomain>` so the existing wildcard certificate covers it. Non-production deploys and promotions never touch `projects.production_deployment_id`. Today one workload runs per project (the latest deployment); a production promote or rollback re-points it. | Fits D14's one-level wildcard constraint and keeps production promotion history/compatibility intact. | `env.<slug>.<domain>` (needs a second wildcard). |
| D45 | **Builds run only on nodes flagged `can_build`, one at a time.** The Builder claims a queued job with its node token, clones the repo (a private GitHub repo with a one-hour token from Skiff's GitHub App, D164; otherwise the node's optional `SKIFF_GIT_TOKEN` or deploy key), runs the build in a transient `systemd-run` unit (`MemoryMax=2G`, `CPUQuota=200%`, 10-minute wall clock), uploads the zip, and the control plane finalizes it through the normal release/deploy path. **GitHub webhooks require a per-project secret**, or arrive through the GitHub App's own signed webhook (D165); unsigned deliveries are rejected. | Keeps user code off the control plane, bounds build cost, and prevents anyone from triggering builds on a public repo. | Building inside the control plane; unsigned webhooks for convenience. |
| D46 | **CLI profiles live in the one config file.** `~/.config/skiff/config.json` holds `profiles.<name>.{url,contentDomain,token}` plus `activeProfile`. Selection is `--profile` > `$SKIFF_PROFILE` > the active profile > the only profile when exactly one exists; with several and no active, commands refuse to guess and list them. Legacy single-profile files are read as profile `default` and upgraded on the next write. `skif profile list\|add\|use\|remove\|show\|current` manages them; `logout --all` removes all profiles. | One machine routinely targets production, staging and a local dev server. Named profiles keep the non-secret URL/domain next to the key, avoid env-var juggling, and still let CI run statelessly with `SKIFF_URL`/`SKIFF_TOKEN` (no profile required). | A separate config directory per deployment (has to be wired into every shell/launcher); per-project profiles (profiles belong to deployments, not projects); requiring `--profile` once more than one exists (breaks the common single-deployment case). |
| D47 | **Any node can be a Builder; the role is a dashboard toggle.** Amends D45: the edge is not excluded. Every node runs `skiff-builder.service` (`skiff-agent builder`, from the agent binary already on the node, using its node token) and idles until a platform admin sets `can_build` from **Nodes → Edit node** or `PATCH /api/v1/nodes/:id`. The daemon is root only to start each build with `systemd-run` as the unprivileged `skiff-build` user, in a sandbox that can write only its checkout and cannot read `/etc/skiff`, `/var/lib/skiff` or `/run/skiff`. Builds never see the node token. The same edit surface changes a node's name, address and workload-slice memory/CPU weight; the memory budget cannot drop below current reservations (D42). | Small fleets often have only the edge, or several equivalent workers. Making builds depend on a separately installed homelab daemon left the role toggle doing nothing on most nodes. | A separate `skiff-builder` binary and installer path; running builds inside the agent's 192 MB sandbox; a build verb on `skiff-helper` (more privileged surface for the same result); keeping edge builds forbidden. |
| D48 | **Node storage locations are a dashboard setting, applied by a root oneshot on the node.** Each node stores `storage_data_dir` (agent state and release cache, which Caddy serves from) and `storage_build_dir` (Builder scratch); `null` keeps the install defaults (`/var/lib/skiff/agent`, `/var/lib/skiff-builder`). They reach the node in desired state. The agent cannot move its own data (its sandbox only writes the current paths), so it drops `/run/skiff/storage.request`, and `skiff-storage.path` runs `skiff-agent storage apply` as root. That command ignores the request's contents, fetches the paths from `GET /api/agent/storage` with the node token, and re-checks them against the shared rules in `@skiff/contracts` (absolute, normalized, not a system tree, other Skiff state, `/home` or a bare mount root). A data move stops the agent, copies with `cp -a`, re-points site links, sets `SKIFF_DATA_DIR` in agent.env, adds a `ReadWritePaths=` drop-in, starts the agent, and deletes the old copy only once the agent has stayed up. Any failure rolls back. Moves wait for running builds. The result is written to `/etc/skiff/storage.json` and relayed in heartbeats. Control-plane data (`/var/lib/skiff/data`) is out of scope. | Operators outgrow the root partition after install; moving by hand means editing units, env files and symlinks consistently on every node. | Letting the agent move data itself (needs a writable `/`); trusting paths written by the agent; mount/bind-mount instructions only; copying and keeping the old copy forever. |
| D49 | **Mass actions and prune share one Operation primitive**: plan → (review) → apply, per-item status persisted as it runs, resumable after a restart, SSE progress, one `applying` run per org per kind. Actions are registered `ActionDefinition`s whose metadata lives in `@skiff/contracts`, so the dashboard, CLI and MCP list them without new plumbing (docs/OPERATIONS.md). | One place for progress, audit, limits and cancel; a future mass action is one definition. | A `/projects/bulk-*` endpoint per action; client-side loops over single-item endpoints (no progress, no resumption, no grouped audit). |
| D50 | **Explicit targets only.** Bulk operations take a list of slugs/ids (≤100, ≤25 over MCP). Filters (`--match`, not deployed, older than) are resolved by the client into that list before planning. | The human confirms exactly what is acted on; a project created after the confirmation can't match a filter and be deleted. | Server-side filter selectors for destructive actions. |
| D51 | **Per-item success.** Each item is idempotent, runs in its own transaction with its own audit row (`audit_log.operation_id`), and is re-verified at apply time; `partial` is a valid outcome. | Items have side effects outside SQLite (Cloudflare, agents, object store) that can't be rolled back; one failure must not block 99 good deletes. | All-or-nothing transactions. |
| D52 | **Prune removes only unreferenced data, always plan-then-apply**, with a 24 h grace window and a 1 h plan expiry. Org scope needs `project:delete`; platform scope (incl. stored objects, which are content-addressed and shared across orgs) needs a platform admin session or API key. Cheap, certain cleanup (trash cascade, old deleted deployments, snapshot GC) stays automatic in the maintenance sweep. | "Not connected" must be seen before it runs; the grace window protects in-flight uploads and deploys. | Pruning "unused" but owned resources; one-shot prune; prune over MCP. |
| D53 | MCP gets **`delete_projects`** (≤25, one elicitation listing every slug, bound to the planned operation id), **`restore_projects`** and `get_operation`. **No purge and no prune over MCP**; 2025-era clients get a dashboard link with the selection. | Keeps D29: agents do reversible things with confirmation, humans gate irreversible ones. | Bulk purge for agents; no bulk tools at all. |
| D54 | The dashboard has a **Trash** view (bulk restore / delete permanently) and bulk delete offers **Undo**; restore re-checks the project quota. Typed confirmation for ≥5 items, any live site, and every permanent delete. | Mass delete needs a visible, fast way back. | Restore through the API only. |
| D55 | **Managed databases are org resources run as tier-3 containers** ([DATABASES.md](./DATABASES.md)). A `databases` row (not a project) is sent to its node as a container `WorkloadDesired` with a `database` field; it sits in `skiff-workloads.slice` and counts toward the node's admission budget (D42). Placement is resolved at create time; moves follow D97. | Reuses the helper, slice, heartbeat and log paths already hardened for apps; no second runtime. | Databases as a project runtime (they have no releases, routes or deployments); a shared Postgres cluster with one database per tenant (one noisy tenant affects all, no per-database limits); a host-installed Postgres (root package management on every node). |
| D56 | **Managed services never bind a public address.** Databases publish on `127.0.0.1` and the `skiff-workloads` Podman network. Same-node consumers get `127.0.0.1:<hostPort>` (process apps) or `db-<id>:5432` (container apps); consumers on other nodes reach the service over the private overlay through a loopback service endpoint ([CLUSTERING.md](./CLUSTERING.md) §4.3). Until that ships, a project with attachments is placed on the service's node. Connection values (`<PREFIX>_URL` etc.) are injected at activation only, and the activation version covers attachments. | `public_address` is not guaranteed to be private, and binding a database to the edge's public IP would expose it. | Binding to `public_address`; injecting the URL into the project spec (would put a password in desired state). |
| D57 | **Database stats go to the telemetry store (D101) through the existing telemetry batch.** The agent samples `pg_stat_database`/`pg_stat_activity` every minute as a `skiff_monitor` role (`pg_monitor` only, bootstrapped by the agent with the owner credentials, held in memory only) and sends gauges plus counter deltas; `db_metrics_1m` rolls up into `db_metrics_1h` with traffic's retention. The latest top-50 table snapshot lives in SQLite. | One ingest path, one retention policy, one store for every time series (D15); the control plane never needs network reach to a database. | Querying databases from the control plane (no route to the node's loopback); a Prometheus postgres_exporter per database (an extra process per DB and a scrape stack D15 rejected). |
| D58 | **Database credentials are sealed with the org key and never reach MCP.** `GET /databases/:name/credentials` needs `database:credentials` (never pre-ticked for agents), works from a dashboard session or an API key holding that permission (so `skif db credentials` works), and is audited. Core refuses MCP principals even when they hold the permission (`requireCredentialReveal`); agents get the URL injected into apps instead. The same rule covers named database credentials (D134), storage keys and broker credentials. | Agents don't need the password to build working apps; keeps D18's write-only spirit for anything an agent can see. | Readable credentials over MCP; storing them as ordinary org secrets (they'd show up in, and could be deleted from, the secrets list). |
| D59 | **Database delete is soft for 7 days and refused while projects are attached.** The container stops but the data dir stays, so restore is lossless. Purge goes through desired state (`databasePurges`) to a fixed helper verb that removes only `<stateDir>/<id>`, then the row is deleted on the agent's report. | Data loss must be reversible like project deletes (D29); the helper keeps fixed verbs only (D43). | Hard delete; deleting the data dir whenever a workload leaves desired state (a transient desired-state bug would wipe data). |
| D61 | **Engines are a registry, and the helper derives the image itself.** The wire carries only `engine` + `version` (engines: D95); the helper maps them to a fixed image, user, mounts and port. | The helper must not run an arbitrary image with database privileges (chowned data dir); a registry makes a new engine a data change, not a rewrite. | Sending the image from the control plane; hard-coding Postgres across services. |
| D62 | **Managed object storage is org resources run as tier-3 containers** ([OBJECT-STORAGE.md](./OBJECT-STORAGE.md), S1). A `storage_instances` row (not a project) is a RustFS instance placed on a node (one server today; replication and multi-drive are [CLUSTERING.md](./CLUSTERING.md) §10), in `skiff-workloads.slice`, admitted against the node budget (D42). Namespace `storage` already means node storage (D48), so wire fields are `objectStorage`/`storageRoutes`/`storagePurges`. | Reuses the database runtime profile, helper, heartbeat and log paths; per-instance limits mean one noisy tenant cannot starve the fleet. | A shared S3 cluster with a bucket per tenant (same reasoning as D55); storage instances as projects (no releases, routes or deployments). |
| D63 | **RustFS's built-in console is off** (S2); Skiff is the only bucket/key management surface. | Keeping a second admin UI would make Skiff's desired state diverge from reality; the console also needs its own exposure and auth story. | Exposing the console; per-instance console credentials. |
| D64 | **S3 exposure is a per-instance toggle: private by default, public via a dedicated route** on `<name>--s3.<contentDomain>` (S3). The route has no `forward_auth`, no site config and byte-for-byte proxying with `Host` preserved both hops, `flush_interval -1` and long timeouts; path-style only. `public_host` has a global unique index and the environment slugs `s3`/`console` are reserved. | S3 clients carry no cookies, so the SigV4 signature is the access control; proxying unchanged keeps presigned URLs and multipart uploads working. One wildcard level fits D14/D44. | Virtual-hosted-style buckets (needs a second wildcard); `forward_auth` in front of S3 (clients can't authenticate); terminating S3 TLS inside the container. |
| D65 | **Buckets and scoped keys are desired state, converged by the agent over loopback** (S4). The instance's workload lists buckets and `SKF*` users; the agent creates buckets, sets `public-read` policies, deletes only through an explicit `deleteBuckets` entry, and creates IAM users limited to their grants. The root key is fetched at activation and held in agent memory only; attachment secrets never reach the helper or disk. | A transient desired-state bug must never wipe data (as D59); apps get scoped keys instead of the root key, and no credential is stored on the node. | Deleting buckets that disappear from desired state; one shared non-root key per instance (no per-app grants); writing the root key into the unit/env file. |
| D66 | **Storage attachments inject S3 settings at activation; private instances follow D56, public instances work from any node** (S5). Attach injects `<P>_ENDPOINT_URL`, `<P>_ACCESS_KEY_ID`, `<P>_SECRET_ACCESS_KEY`, `<P>_REGION=us-east-1`, `<P>_FORCE_PATH_STYLE=true`, `<P>_PUBLIC_ENDPOINT_URL` (public only) and `<P>_BUCKET` (single grant); the prefix defaults to `S3` and `AWS` matches the AWS SDKs. | Private S3 must not bind a public address (D56); a public instance's TLS-authenticated S3 is safe from anywhere. Activation-time injection keeps secrets out of desired state (D18/D43). | Binding private S3 to `public_address`; putting credentials in the project spec; requiring a redeploy for attach/detach. |
| D67 | **The root key is sealed with the org key and revealed only to humans** (S6): `GET /storage/:name/credentials` needs `storage:credentials` and every read is audited; MCP never returns keys. Attachment keys are not revealable; rotation creates a new pair, lets the agent create it, re-activates consumers, then deletes the old one. | Mirrors D58: agents don't need the root key to build working apps. | Readable credentials over MCP; deriving app keys from the root key at read time. |
