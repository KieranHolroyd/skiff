# Skiff — GitLab, Gitea and Forgejo

Status: **built 2026-11-08** (§2 → D173, §3 → D174, §4 → D175, §5 → D176, §7 → D177). What is not
built is listed in §9. GitHub keeps its App ([GITHUB.md](./GITHUB.md)); this document gives every
other forge the same features through one abstraction.

GitHub has an App: one registration, installations per account, one-hour tokens per repository and
a single webhook. GitLab, Gitea and Forgejo have none of that. What they do have is a REST API that
a token can drive: list repositories, create webhooks, post commit statuses, read files, and (on
GitLab) mint deploy tokens. Skiff therefore models them as **connections**: an organisation stores a
forge's base URL and an API token, and Skiff does with that token what the App does on GitHub.

---

## 1. Summary

| GitHub App feature (GITHUB.md) | GitLab | Gitea / Forgejo | Decision |

## 2. Connections (D173)

`forge_connections` (migration 0094) holds one row per (org, base URL):

| Column | Meaning |
|---|---|
| `kind` | `gitlab`, `gitea` or `forgejo` |
| `base_url` | `https://gitlab.com`, `https://codeberg.org`, `https://git.example.com/gitea` (a sub-path is allowed) |
| `token_sealed` | API token, sealed with the org's data key. GitLab: `api` scope (a group access token with *Maintainer* is best). Gitea/Forgejo: `write:repository` + `read:user` (+ `write:organization` for organisation hooks). |
| `clone_token_sealed` | Optional read-only token build nodes may receive (GitLab `read_repository`; Gitea/Forgejo `read:repository`). |
| `webhook_secret_sealed` | Generated by Skiff; every hook it creates uses it. |
| `account_login` / `clone_login` | Who the tokens belong to, from `GET /user` when saved. |

`ForgeService.create` proves the token (`GET /user`) before storing anything, and proves the clone
token separately. The API token never leaves the control plane. Only owners and admins of the
org add, change or remove connections (`build:create` plus role, like automatic pipeline setup).

**Egress.** Base URLs are typed by org admins, so the control plane must not become a way into its
own network. As for log drains, a host that is (or resolves to) a loopback, private, link-local or
CGNAT address, or a `.local`/`.lan`/`.internal` name, is refused unless a platform admin connects it,
which sets `allow_private_network` (migration 0095; a homelab Gitea is exactly that case). For every other
connection each request re-resolves the host and refuses a private answer (DNS rebinding).

**Which connection serves a URL.** `parseRepoUrl` turns `https://host[/base]/group/sub/repo(.git)`,
`git@host:group/repo.git` and `ssh://git@host[:port]/group/repo.git` into a host and a path. A
connection serves a URL when the host matches and the path starts with the connection's base path;
the rest is the repository's full name (GitLab names may be nested: `group/sub/repo`). Repository
keys are `host/full name`, lower case, so `acme/app` on GitHub and on GitLab never meet.

**Repositories.** `GET /api/v1/git/repositories` merges the GitHub App's repositories (GITHUB.md §6)
with every connection's: GitLab `GET /projects?membership=true&min_access_level=30` (Developer and
up, not archived, most recently active first), Gitea/Forgejo `GET /user/repos`. Each row says its
provider and connection, so a picker can show one list.

## 3. Webhooks (D174)

Each connection has one receiver, `POST /api/webhooks/forge/<connection id>`. Skiff creates the
hooks itself:

- **Per repository.** When a git source, a pipeline repository or an import names a repository a
  connection serves, `ensureWebhook` looks for a hook with Skiff's URL (`GET …/hooks`) and creates
  one if none exists (GitLab: push + merge request events; Gitea/Forgejo: push + pull request,
  type `gitea`, JSON). The hook id is recorded in `forge_webhooks`. Failures are kept on the row
  and shown on the connection page, with a retry. Like installing the GitHub App, adding a
  connection (or replacing its token) runs `backfill`: every enabled git source and pipeline
  repository the connection serves gets its hook then, so repositories set up earlier need nothing.
  A pipeline repository with no runs yet shows a missing hook in its set-up steps, with **Create the
  webhook** (`ForgeService.coverage` / `hookRepository`).
- **Per namespace.** "Receive events for a whole group / organisation" creates one group hook
  (GitLab Premium or self-managed with the feature) or organisation hook (Gitea/Forgejo, free).
  Repositories under it need no hook of their own, and pushes to repositories Skiff does not know
  yet can add them to Pipelines (§7).

**Verification.** GitLab sends the secret verbatim in `X-Gitlab-Token`, compared in constant time.
Gitea and Forgejo sign the body (`X-Gitea-Signature` / `X-Forgejo-Signature`, hex HMAC-SHA256).
Unsigned deliveries are refused (D45 holds).

**Normalised events.** `normaliseForgeEvent(kind, headers, payload)` (pure, unit tested) turns a
GitHub, GitLab, Gitea or Forgejo delivery into one `ForgeEvent`:

- `push`: ref, after, deleted, commit file lists (null when the forge truncated them: GitHub lists
  20 commits, GitLab 20 with `total_commits_count`), head message, actor, repository full name,
  clone URL and default branch;
- `pull_request`: action (Gitea's `synchronized` → `synchronize`; GitLab `open`/`reopen`/`update`
  with new commits → `opened`/`reopened`/`synchronize`), number, title, head sha and branch, base
  branch, whether head and base are the same repository, and the ref to fetch (`refs/pull/<n>/head`,
  or GitLab's `refs/merge-requests/<iid>/head`).

Builds (`BuildService.handlePush`) and pipelines (`PipelineService.handleForgeEvent`) take a
`ForgeEvent` and a repository key, so GitHub's App, GitHub's hand-made webhooks and every forge go
through the same code.

**Hand-made webhooks.** `/api/webhooks/github/<project>` (also reachable as
`/api/webhooks/git/<project>`) and `/api/webhooks/pipelines/<id>` accept all three formats, each
verified with the stored secret: `X-Hub-Signature-256`, `X-Gitea-Signature`/`X-Forgejo-Signature`
or `X-Gitlab-Token`. When a Skiff-created hook (repository or namespace) already delivers that
repository, the hand-made one is accepted and ignored, as with the App.

## 4. Clone credentials (D175)

The build claim's `auth` and the pipeline claims' `gitToken` gain a host and a user name
(`auth.host`, `gitTokenHost`, `gitTokenUsername`). The Builder sends the token only to that host
(`gitAuthEnv`), as an `http.extraHeader` in the clone process's environment, exactly as for the App.
Builders older than this change only ever send a claim token to `github.com`, so for them the
node's own credentials apply.

- **GitLab:** `POST /projects/:id/deploy_tokens` with `read_repository`, named `skiff-clone`,
  expiring after two days; cached for one day per repository. That is GitLab's closest match to an
  installation token: one repository, read-only, short-lived. It needs *Maintainer* on the project;
  without it the connection's clone token is used, else none. Expired `skiff-clone` tokens are
  revoked when a new one is minted.
- **Gitea / Forgejo:** neither has repository-scoped HTTPS tokens, so only the optional clone
  token is sent. The connection page recommends a bot account that can read only the repositories
  Skiff builds.

## 5. Statuses and deployments (D176)

`GitProviders` (`core.git`) is the one place builds and pipelines report to: it routes a
repository URL to the GitHub App or to the connection that serves it.

| Skiff state | GitHub | GitLab | Gitea / Forgejo |
|---|---|---|---|
| queued | pending | pending | pending |
| building / running | pending | running | pending |
| succeeded | success | success | success |
| failed | failure | failed | failure |
| cancelled / error | error | canceled | error |

Contexts are unchanged (`skiff-build/<project>`, `skiff/<workflow>`; GitLab calls it `name`). A
succeeded git build also records a GitLab deployment (`POST /projects/:id/deployments`, status
`success`, environment `<project>` or `<project>-preview`). A pipeline repository's stored status
token (PIPELINES.md WP3) now works for GitLab, Gitea and Forgejo repositories too; the API base is
taken from the connection that serves the URL, else from the clone URL's origin.

## 6. Surfaces

- **Settings → Git providers** (`/settings/git`): the GitHub App's state with a link to its page,
  then the org's connections: add (kind, base URL with gitlab.com / codeberg.org presets, token,
  optional clone token), the account each token belongs to, the hooks Skiff created (with errors and
  retry), "Receive events for a whole group / organisation", update tokens, remove (deletes the hooks
  Skiff created, best effort).
- **Pickers.** `GitRepoPicker.svelte` replaces `GithubRepoPicker` in the git source, pipeline
  repository and import forms and lists every provider.
- **Views.** `GitSourceView` and `PipelineRepositoryView` gain `gitProvider`
  (`{ kind, connectionId, delivered }`), which switches webhook copy to "delivered by GitLab" etc.
- **REST.** `GET/POST /api/v1/git/connections`, `GET/PATCH/DELETE /api/v1/git/connections/<id>`,
  `POST /api/v1/git/connections/<id>/webhooks` (`{ repository }` or `{ namespace }`),
  `GET /api/v1/git/repositories`, `GET /api/v1/git/detect`, `POST /api/v1/git/import`.
- **MCP.** `list_git_repositories` (read-only, `build:read`) and `deploy_from_git`;
  `list_github_repositories` and `deploy_from_github` stay.
- **Pipeline repositories** take `provider: github | gitlab | gitea | forgejo | generic`, inferred
  from the clone URL when a connection serves it.

## 7. Deploy from Git, and pipelines on push (D177)

`/new/git` (and `/new/github`, which now lists every provider) is GITHUB.md §9 with a provider per
repository. `GitImportService` reads the repository through `core.git.readPath` (GitLab
`repository/tree` + `repository/files`; Gitea/Forgejo `contents`), runs the same
`detectFramework`, and creates project, git source (its webhook through `ensureWebhook`), first
build and pipeline repository. `githubImportSchema` keeps working; `connectionId` selects a forge.

**Pipelines set themselves up** (GITHUB.md §10) for a push that arrives through a connection's
namespace hook to a repository the org has no pipeline repository for: same rules (branch pushes
only, never merge/pull requests, ten-minute negative cache, ignore list, on/off switch), the
connection's creator as `createdBy`. Ignore-list entries for forges are `host/full name`
(`gitlab.com/acme/api`); GitHub's stay `owner/repo`.

## 8. Registry trust and sign-in (D178)

**GitLab CI → registry.** A trust may name `provider: gitlab`, an issuer (the GitLab base URL,
default `https://gitlab.com`) and a project path. A job requests
`id_tokens: { SKIFF_ID_TOKEN: { aud: <registry host> } }` and logs in as `gitlab-oidc` with it. The
realm fetches the issuer's keys through its discovery document, checks RS256, issuer, audience and
time, then matches `project_path` and `refs/heads/<ref>` or `refs/tags/<ref>` (from `ref` and
`ref_type`) against the org's trusts. Migration 0094 rebuilds `registry_oidc_trusts` without the
`provider IN ('github')` check and adds `issuer`.

**Sign-in.** GitLab, Gitea and Forgejo are OpenID Connect providers, so an org can use any of them
through Settings → Single sign-on; the preset list has GitLab, Forgejo and Gitea (GitLab's issuer has
no trailing slash, Gitea/Forgejo's `ROOT_URL` has one). A platform-wide "Continue with GitLab"
button reads `GITLAB_CLIENT_ID`, `GITLAB_CLIENT_SECRET` and optional `GITLAB_ISSUER` (self-managed)
at boot, like `GITHUB_CLIENT_ID`; `gitlab` is a sign-in method an org's auth policy can allow or
refuse, like `github`.

## 9. Not built

- **Runner pools** for GitLab Runner and Forgejo/Gitea act_runner. GitHub's pool works because
  GitHub mints single-use JIT configs (RUNNERS.md). The plan: GitLab `POST /user/runners` per pool
  plus `gitlab-runner run-single --max-builds 1` per replica; Forgejo/Gitea registration tokens plus
  `act_runner daemon --once` (`--ephemeral`). Each needs its own image, template and activation
  path.
- **A job token like `GITHUB_TOKEN`.** No forge here can mint a short-lived, repository-scoped API
  token from a stored credential, and handing jobs the connection's long-lived token would break
  D164's rule. Add a pipeline secret instead.
- **OIDC trusts for Gitea/Forgejo Actions.** Their ID-token support is new and differs by version;
  the realm's verifier is issuer-generic, so adding them is a claims mapping once it settles.
- **Merge request comments, check runs, preview deployments per MR.** As on GitHub (GITHUB.md §8).
- **Bitbucket, Azure DevOps, Gerrit, SourceHut.** The `ForgeClient` interface is the seam; each
  needs a client and an event normaliser.
- **System hooks** (GitLab instance-wide, Gitea/Forgejo admin hooks). They need an admin token, and
  a namespace hook covers the same need for one org.
