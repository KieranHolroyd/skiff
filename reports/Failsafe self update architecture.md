# Make Skiff's updater outlive its own bugs

Skiff cannot make every update succeed, but it can make every failure harmless and temporary. To get there it should adopt the shape that every mature updater shares, from Android A/B to OSTree, RAUC, Home Assistant OS and Kamal. The new release arrives prebuilt, signed and immutable, and is staged beside the running one. Checks that the *new* release owns verify it. A single pointer flips. The new release then runs as a trial and is committed only on a positive health signal, judged by an arbiter that is not part of the payload. The 2026-11-05 incident was not a canary failure: the canary did its job by refusing to flip. It was a layering failure. The code that decided whether a new release was acceptable lived inside the *old* release, so one bug vetoed every successor. The blocklist then recorded each of those wrongly blamed rejections as a permanent skip. Home Assistant's Supervisor fell into the same trap in 2022 and needed an out-of-band script to escape. The recommended architecture has six parts. A tiny, separately versioned **stage-0 updater** lives outside `/opt/skiff/releases`. **CI-built, signed artifacts** are described by a signed manifest. **Release-owned hooks** run self-checks and migration rehearsals. **Blue/green** runs two systemd template units switched by a Caddy admin-API PATCH. **Expand-only migrations** make rollback a code-only, lossless operation. **Failure attribution** lets only release-caused failures blocklist a version. The work fits a five-phase migration plus a Phase 0 that unblocks the stuck host today.

## The incident was a layering failure, not a canary failure

Two properties together define "an update cannot fail" in the sense Skiff wants. **Safety**: no update can leave the host worse than the last committed release. **Liveness**: a bug in one release can never stop a later release from landing. Mature systems treat these as separate obligations. Android defines a "successful" slot as one that can "boot, run, and update itself" ([Android A/B](https://source.android.com/docs/core/ota/ab)). ChromeOS's original design counts a boot as successful only "if the updater process can successfully launch" ([Chromium OS Autoupdate](https://www.chromium.org/chromium-os/chromiumos-design-docs/filesystem-autoupdate/)). Both make liveness part of the definition of healthy. Pengutronix, RAUC's maintainers, start from the premise that field errors happen however hard a release was tested, so the mechanism has to tolerate bad releases rather than assume good ones ([Pengutronix](https://www.pengutronix.de/en/blog/2019-08-16-rauc_maintenance.html)).

Skiff's current updater gets safety mostly right and liveness wrong. The canary blocked both bad flips, the old symlinks stayed intact, and the host kept serving. The failure lay elsewhere: `/usr/local/sbin/skiff-update-self` execs `scripts/update-self/main.ts` from `/opt/skiff/current`. The **acceptance test for release N+1 was therefore code from release N**. The chown-before-mkdir bug in N's canary preparation made every candidate's `/readyz` report "data dir objects not writable", whatever that candidate's quality. The blocklist in `/opt/skiff/update-state.json` then charged both rejections to 0.6.2 and 0.6.3, the releases that were innocent. Home Assistant's November 2022 incident has the same anatomy. Supervisor 2022.11.0 "prevents the Supervisor from working properly and from updating itself to a working version", and recovery needed `curl … update-supervisor.txt | sh`, served from the version server and independent of the broken Supervisor ([HA community](https://community.home-assistant.io/t/supervisor-november-beta-issue-impacting-users-on-home-assistant-beta-dev-channels/489895)).

The table below compares Skiff with the invariants that A/B and atomic-update systems state, nearly word for word, across projects.

| Invariant | How mature systems state it | Skiff today | Gap |
|---|---|---|---|
| Never modify the running version | "Not even the autoupdater will edit the currently-booted root file system" ([ChromeOS](https://www.chromium.org/chromium-os/chromiumos-design-docs/filesystem-autoupdate/)); slot targets "must contain only inactive slots" ([RAUC](https://rauc.readthedocs.io/en/latest/basic.html)) | New release goes into its own `releases/<UTC>-<sha12>` dir | Met |
| Verify the payload before activating it | Signing is mandatory in RAUC; Android re-reads and verifies partitions before switching | Payload is a GitHub source tarball **built on the host**, unsigned | Build environment is on the critical path; no integrity anchor beyond TLS |
| One atomic pointer flip | OSTree swaps a fully populated directory via one symlink ([OSTree](https://ostreedev.github.io/ostree/atomic-upgrades/)) | `rename(2)` of `current`/`previous` symlinks | Met, but the control plane stops *before* the new one starts, so the flip costs downtime |
| Old version stays bootable until commit | "The currently booted deployment must always be in the new set" ([OSTree](https://ostreedev.github.io/ostree/atomic-upgrades/)) | `previous` kept | Met |
| Default to revert, with an independent arbiter | The bootloader or a verifier daemon decides; a boot counter is decremented *before* the trial ([systemd boot assessment](https://systemd.io/AUTOMATIC_BOOT_ASSESSMENT/)) | The updater process that performs the swap also decides whether to roll back; no armed counter survives that process | A crash, kill or reboot mid-swap leaves no one to revert |
| Healthy means "can update itself" | Android, ChromeOS (above) | Not checked | A release that breaks the update path can be committed |
| Retry is safe and failures are attributed correctly | A failed apply touches only the unused slot and "the client is free to re-attempt" ([Android A/B](https://source.android.com/docs/core/ota/ab)) | Every failure blocklists the candidate | **An updater bug becomes a permanent update block** |

The last two rows explain the incident, and they show where the fix belongs. A more careful canary would not have helped. What Skiff needs is to move the canary's *ownership* and to make the blocklist *trust its own verdicts less*.

## Mature updaters stage, flip once, and default to revert

Android, ChromeOS, OSTree/bootc, NixOS, systemd-sysupdate, Mender and RAUC all structure an update the same way. They write the new version where the running system never looks, verify it, flip one pointer, and treat the result as provisional until something commits it. Android's `update_engine` writes and verifies the unused slot and only then calls `setActiveBootSlot()`, warning that "marking the unused slot as active doesn't mean it will finish booting". Before writing anything it calls `markBootSuccessful()` on the *current* slot, so it can never fall back into a half-written one ([Android A/B](https://source.android.com/docs/core/ota/ab)). systemd encodes tries in the boot entry's filename (`+3` → `+2-1` → … → `+0-3`). The bootloader decrements the count on each attempt, `systemd-bless-boot` clears it only when `boot-complete.target` is reached, and a `+0` entry sorts last so the old version boots ([systemd boot assessment](https://systemd.io/AUTOMATIC_BOOT_ASSESSMENT/)). Mender names the commit point explicitly. After `ArtifactCommit_Leave` "it is too late to go to an Error script", and every state script has a hard timeout after which "the Mender Client will treat the script and the update as failed" ([Mender](https://docs.mender.io/artifact-creation/state-scripts)).

These designs share three properties that Skiff's updater lacks. First, **the arbiter is never the new code**. Only a bootloader, a separate verifier or an external client can veto. The new version can vote "good" but cannot block a fallback. Home Assistant OS layers this cleanly: RAUC and the bootloader in the OS image own rollback, and the separately updated Supervisor "marks the booted slot as good" once it starts. "If it never gets marked as good, the bootloader falls back to the other slot" ([HA OS update system](https://contributors.home-assistant.io/os/operating-system/update-system/)). Second, **the counter is armed before the trial**. A crash, hang or power cut therefore converges on the old version without any code having to "handle" the failure. Third, **every wait is bounded**. greenboot adds a watchdog grace period and caps attempts ([greenboot](https://github.com/fedora-iot/greenboot)). systemd warns that a health check started *after* `boot-complete.target` is reached gates nothing ([systemd boot assessment](https://systemd.io/AUTOMATIC_BOOT_ASSESSMENT/)).

The documented failures confirm the pattern by violating it. In a 2026 amateur-radio A/B build, a trial slot hung at a blinking cursor because OTA rewrote only the rootfs while the kernel sat on a static shared partition. "the trial slot literally could not boot its own userland." The fix was to put everything a slot needs inside the slot ([Hackaday OE5XRX](https://hackaday.io/project/205911-oe5xrx-open-source-modular-remote-ham-station/log/249081-a-blinking-cursor-a-bricked-slot-and-making-ota-unbrickable)). For Skiff, the "shared kernel" equivalents are anything outside `releases/<v>` that a release silently depends on: unit-file drop-ins, data-directory ownership, Caddy config, and the helper's protocol. Each of these has to be either shipped inside the release or version-checked by it.

These mechanisms translate to a single userspace host almost one for one. Release directories are the slots and the `current` symlink is the active pointer. A small trial-state file stands in for the boot counter. A systemd unit that is *not* upgraded in the same transaction plays the bootloader. systemd-sysupdate is the strongest off-the-shelf alternative to writing this yourself. It already provides URL-tar sources, `Verify=` against `SHA256SUMS.gpg`, `InstancesMax=` retention, `ProtectVersion=%A` for the running version, and `CurrentSymlink=` ([sysupdate.d(5)](https://www.freedesktop.org/software/systemd/man/latest/sysupdate.d.html)). It does not provide the trial, health gate or revert, and that is the part Skiff got wrong. Adopting it for fetch-and-verify is reasonable. It still leaves the arbiter to be built.

## Building on the host puts the riskiest work on the critical path

Skiff's step 3 (`bun install --frozen-lockfile`, then four Vite builds at a 3.2 GB peak) is the pattern behind the most-reported self-hosted update failures. Discourse builds its image on the host. In April 2025 a 2 GB instance failed to bootstrap because the Ember build used up RAM plus swap, and the team confirmed that 2 GB "is enough for docker rebuilds, but not for the web upgrader to work" ([Discourse Meta](https://meta.discourse.org/t/high-rebuild-memory-requirements-april-2025-edition/360419)). Coolify's backups failed when ghcr.io rate-limited a helper-image pull ([coolify#3355](https://github.com/coollabsio/coolify/issues/3355)). Its upgrade script has to detect and abort on a specific Docker Engine 27.0–28.0.0 bug ([upgrade.sh](https://raw.githubusercontent.com/coollabsio/coolify/main/scripts/upgrade.sh)). Memory, registries, lockfiles and toolchain drift are each a way to fail that has nothing to do with the release's quality. The incident bug belongs to the same family: it existed only because the updater *assembled* a runtime environment imperatively on the host (mkdir as root, chown to skiff) instead of receiving one already built.

Every system surveyed ships the payload prebuilt and verified, and the client only copies, checks and flips. HAOS ships signed RAUC bundles, and "RAUC checks the signature against the keyring … before it installs anything" ([HA OS update system](https://contributors.home-assistant.io/os/operating-system/update-system/)). ONCE, Tailscale and Caddy ship per-arch binaries ([ONCE updater.go](https://github.com/basecamp/once/blob/main/internal/version/updater.go), [Caddy CLI](https://caddyserver.com/docs/command-line)). For a SvelteKit-on-Bun app, `@sveltejs/adapter-bun` with `compile: true` emits a single executable that "embeds the server code, client assets, prerendered output, and Bun runtime". It supports cross-compiling to `linux-x64` and needs Bun 1.4 or newer ([adapter-bun](https://svelte.dev/docs/kit/adapter-bun)). One caveat is specific to Skiff: the control plane depends on `@duckdb/node-api`, a native addon, and compiled `.node` addons cannot be embedded. That package has to be marked external and shipped beside the executable. The lower-risk first step is therefore a CI-built tarball of `build/`, production `node_modules` and the pinned Bun runtime. Skiff already pins a runtime per release: the unit execs `/opt/skiff/current/control-plane/runtime/bun`. The single binary can follow once DuckDB's packaging is proven.

Prebuilt artifacts also make a trust anchor possible. Tailscale's distsign is the right size for Skiff. Offline Ed25519 root keys sign online signing keys, which sign each artifact, and the client verifies before installing ([tailscale PR #8943](https://github.com/tailscale/tailscale/pull/8943)). TUF adds two cheap protections: versioned metadata stops a rollback to older software, and expiring metadata exposes a "freeze" ([TUF security](https://theupdateframework.io/security/)). Skiff can get both without running a TUF repository. It needs a signed `manifest.json` with a monotonically increasing serial and an expiry, and the updater rejects any serial below the last one seen or any expired manifest. Tailscale's own error message holds a warning, though: verification failure may mean "a very old client with outdated root keys" ([distsign](https://pkg.go.dev/tailscale.com@v1.84.2/clientupdate/distsign)). Key rotation is therefore itself a liveness risk, and the updater must accept a root-signed list of signing keys rather than one baked-in key. GitHub artifact attestations can sit on top for provenance ([GitHub docs](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)). They should be optional at verify time so a GitHub or Sigstore outage cannot block an update.

The signed manifest also gives the release side its kill switch. Home Assistant promotes builds dev → beta → stable by editing `stable.json`. When Supervisor 2022.11.0 broke, "users on stable releases were not affected" ([HA community](https://community.home-assistant.io/t/supervisor-november-beta-issue-impacting-users-on-home-assistant-beta-dev-channels/489895)). CrowdStrike's July 2024 outage is the counterexample: a template expecting 21 fields received 20, slipped past a validator logic error, and went everywhere at once. The remediation was staged roll-out with canary rings ([CrowdStrike RCA](https://crowdstrike.com/wp-content/uploads/2024/08/Executive-Summary_Root-Cause-Analysis_Channel-File-291.pdf)). The most valuable gate for Skiff is cheaper still. **CI should run the exact canary and migration step the host runs**, against the exact artifact, under the production user and sandbox, with fixture databases from N-1, N-2 and an older baseline. With that gate in place, the chown-before-mkdir bug would have failed in CI rather than on the host.

## Zero downtime on one host means two sockets and a Caddy PATCH

Every zero-downtime PaaS surveyed uses the same sequence. Boot the new instance beside the old one, poll its health until it passes or a deadline expires, switch the proxy target in one step, then drain the old instance for a bounded time. kamal-proxy's defaults show the scale: 30 s deploy timeout, 30 s drain, `/up` polled every 1 s with a 5 s per-request timeout ([kamal-proxy service.go](https://github.com/basecamp/kamal-proxy/blob/main/internal/server/service.go)). ONCE, which like Skiff is one product on SQLite, starts a new container on the same data volume and calls `kamal-proxy deploy … --deploy-timeout 120s`. On `target not healthy` it removes the newcomer, and the old container keeps serving ([ONCE application.go](https://github.com/basecamp/once/blob/main/internal/docker/application.go)). Render and CapRover drop to stop-first, with downtime, once a persistent volume is attached ([Render](https://render.com/docs/deploys), [CapRover](https://caprover.com/docs/zero-downtime.html)). That constraint exists because a volume attaches to one machine. On a single host, blue and green can open the same SQLite file, so the limit does not bind Skiff.

Caddy can act as the switch, so kamal-proxy is not needed. kamal-proxy has no unix-socket targets, and adopting it would mean replacing Caddy's TLS. Give the control plane's `reverse_proxy` an `"@id"`, then `PATCH /id/skiff_cp/upstreams` to `[{"dial":"unix//run/skiff/control-green.sock"}]`. Caddy applies admin-API changes as graceful reloads, and "if the new config fails for any reason, the old config is rolled back into place without downtime". `Etag`/`If-Match` guards against concurrent edits ([Caddy API](https://caddyserver.com/docs/api)). Ordinary in-flight requests finish, because the default `grace_period` is "eternal" ([Caddy options](https://caddyserver.com/docs/caddyfile/options)). The sharp edge is long-lived streams: "WebSocket connections are forcibly closed when the config is reloaded" unless `stream_close_delay` is set ([reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)). A June 2026 report confirms this in practice ([Caddy community](https://caddy.community/t/way-to-achieve-zero-downtime-for-existing-connections-when-dynamic-patch-maps/33753)). Every PATCH reloads all sites on that Caddy, including user apps, so `stream_close_delay` belongs on those routes too. `lb_try_duration` (with `lb_try_interval` defaulting to 250 ms) makes Caddy hold and retry requests while no upstream answers ([reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)). That is Skiff's equivalent of kamal-proxy's `pause`. It hides any remaining sub-second gaps today, and it serves as a write fence for the rare migration that cannot be made backward-compatible.

Socket handoff is the obvious alternative (systemd socket activation, the FD store, nginx `USR2`, tableflip), and it is the wrong tool here. Bun does not document listening on an inherited file descriptor: the `Bun.serve({fd})` PR was closed unmerged ([Bun PR #2852 mirror](https://gh.r-mj.com/oven-sh/bun/pull/2852)). Bridging that gap would need `systemd-socket-proxyd`, which is just a second proxy. Handoff also serialises old and new, so it gives "no refused connections" without proving the new code before it owns the listener. Two processes cannot bind one socket path, so the practical design is two template units, `skiff-control-plane@blue` and `@green`, each with its own socket. `Type=notify` would give a real readiness signal ([systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html)). The unit is `Type=simple` today, and Bun's sd_notify support was not verified in this research, so readiness may come from polling the socket instead.

Sharing the database during the overlap is safe if both colours behave. In WAL mode "readers do not block writers and a writer does not block readers", but there is "only one writer at a time" ([SQLite WAL](https://www.sqlite.org/wal.html)). Both colours therefore need `busy_timeout` and `BEGIN IMMEDIATE` for write transactions, so a deferred read does not fail with `SQLITE_BUSY` when it tries to upgrade ([SQLite transactions](https://www.sqlite.org/lang_transaction.html)). Litestream is "just another process" and asks apps to set `busy_timeout = 5000` and `wal_autocheckpoint = 0`. "It is _your_ responsibility" to make sure only one replicator runs ([Litestream tips](https://litestream.io/tips/)). Skiff already runs `skiff-litestream.service` standalone rather than through `-exec`, so blue/green does not disturb replication. The colours must never start their own replicators: two replicators on one database caused a flood of failures in [Litestream #422](https://www.github.com/benbjohnson/litestream/issues/422). Singleton loops, such as schedulers, reconcilers and alerting, need a lease row with holder, generation and `expires_at`, compare-and-set under SQLite's single-writer lock, and idempotent handlers, because delivery is at-least-once ([@rootware/jobs](https://jsr.io/@rootware/jobs/doc/~/DurableJobStore), [MAS worker](https://element-hq.github.io/matrix-authentication-service/rustdoc/src/mas_storage_pg/queue/worker.rs.html)). Green must not start those loops until it is promoted. Blue releases its lease explicitly on drain, so green does not have to wait for it to expire.

A health gate is only as good as the depth of its checks. Fly users saw green machines pass checks "immediately", before they had actually booted ([Fly community](https://community.fly.io/t/blue-green-deployment-always-deploy-instantly/27642)). Kubernetes separates startup, readiness and liveness because each answers a different question ([Kubernetes probes](https://kubernetes.io/docs/concepts/configuration/liveness-readiness-startup-probes/)). The features that make rollback instant are pre- and post-promotion analysis with the old version kept running: Argo's `scaleDownDelaySeconds` defaults to 30 ([Argo Rollouts](https://argo-rollouts.readthedocs.io/en/stable/features/bluegreen/)), and Render keeps the old instance for 60 s ([Render](https://render.com/docs/deploys)). For Skiff, rollback during the bake window should be a PATCH back to a still-running blue, not a restart and certainly not a database restore.

## Lossless rollback requires release N-1 to run on schema N

Skiff's current rollback restores the pre-update snapshot, which throws away every write made after the switch. That is the right *last resort* and the wrong *default*. Mature self-hosted products split into two camps. The first is forward-only migrations with "restore the backup" as the only way back. Coolify warns that "an older Coolify release may not work with database changes made by a newer release" ([Coolify downgrade](https://coolify.io/docs/core/instance-management/downgrade)). Forgejo refuses to start on a newer database ([Forgejo migrate.go mirror](https://git.fb1.uni-bremen.de/davrot/forgejo_backup/src/branch/landingpagedetails/models/forgejo_migrations/migrate.go)). Sentry documents no downgrade at all ([Sentry releases](https://develop.sentry.dev/self-hosted/releases/)). The second camp makes old code compatible with the new schema. GitLab requires compatibility one monthly release either side because "updating GitLab is not atomic" ([GitLab multi-version](https://docs.gitlab.com/development/multi_version_compatibility/)). Mattermost is the exception: it ships down-migration SQL in the *newer* binary and advises against going back more than one major version ([Mattermost](https://docs.mattermost.com/administration-guide/upgrade/downgrading-mattermost-server.html)). The GitLab model is the only one that makes rollback lossless: if N-1 tolerates schema N, reverting is "start the old code on the current database". Data in new columns sits unused until the next roll-forward.

GitLab's incident list reads like a preview of Skiff's blue/green window. A `NOT NULL` constraint broke CI artifacts because old servers kept inserting nulls. A new NOT NULL column broke release creation while canary ran new code. An old-server trigger overwrote a column that new servers wrote ([GitLab multi-version](https://docs.gitlab.com/development/multi_version_compatibility/)). The remedy is expand/migrate/contract in separately shipped steps. Additive "regular" migrations run before deploy. Contracting "post-deployment" migrations run afterwards, even days later. Dropping a column takes three releases: ignore the column, drop it, then remove the ignore rule ([GitLab avoiding downtime](https://docs.gitlab.com/development/database/avoiding_downtime_in_migrations/), [GitLab post-deploy](https://docs.gitlab.com/development/database/post_deployment_migrations/)). Stripe's four-step dual-write does the same for model changes, and makes access to the old field a hard error so nothing quietly keeps depending on it ([Stripe](https://stripe.com/blog/online-migrations)). The split has its own failure mode. Discourse users who left post-deploy migrations unrun later hit duplicate-column errors ([Discourse Meta](https://meta.discourse.org/t/failure-to-pay-attention-to-skip-post-deployment-migrations-causes-problems/221906?tl=en)). Skiff's runner must therefore always apply pending post migrations from older releases before the next release's pre migrations.

SQLite narrows the safe set further. Its `ALTER TABLE` supports only RENAME TABLE, RENAME COLUMN, ADD COLUMN, DROP COLUMN, and, since 3.53.0 (April 2026), SET/DROP NOT NULL. Everything else needs the 12-step rebuild, which drops and replaces the table. A NOT NULL column added with ADD COLUMN needs a non-NULL default. Since 3.37.0, ADD COLUMN with a CHECK fails if any existing row violates it ([SQLite ALTER TABLE](https://www.sqlite.org/lang_altertable.html)). `PRAGMA foreign_keys` "is a no-op within a transaction", and `integrity_check` "does not find FOREIGN KEY errors", so a rebuild needs the pragma toggled outside the transaction and a separate `foreign_key_check` ([SQLite PRAGMA](https://www.sqlite.org/pragma.html)). Old prepared statements re-prepare automatically after a schema change ([sqlite3_prepare](https://www.sqlite.org/c3ref/prepare.html)), so a dropped or renamed column fails at runtime inside the *old* process, not at migration time. Atlas is the only lint tool surveyed with SQLite support and an explicit backward-incompatible analyzer: BC101–104 for renames and drops, MF101/103/104 for data-dependent constraints ([Atlas analyzers](https://atlasgo.io/lint/analyzers)). strong_migrations contributes the "unparseable raw SQL is unsafe unless `safety_assured`" rule ([strong_migrations](https://github.com/ankane/strong_migrations)).

| Class | SQL in Skiff migrations | When it may run | Rollback consequence |
|---|---|---|---|
| Expand (N-1-safe) | `CREATE TABLE`, non-unique `CREATE INDEX`, nullable `ADD COLUMN` or `NOT NULL DEFAULT <const>`, seed `INSERT` | Pre, before green starts | Code-only revert, lossless |
| Data-dependent | `CREATE UNIQUE INDEX` on existing data, `ADD COLUMN … CHECK`, SET NOT NULL | Pre only after rehearsal on the DB copy passes; otherwise post | Lossless if N-1's writes satisfy it, which the N-1 boot test proves |
| Contract (N-1-unsafe) | `DROP`/`RENAME` table or column, 12-step rebuild, triggers that rewrite old writes, format-changing `UPDATE` | Post, only after the release that stopped using the old shape is committed, at the earliest in N+1 | Reverting below it requires snapshot restore, so it is flagged and needs consent |
| Unclassified | Anything the linter cannot parse | Refused without an explicit annotation | Treated as contract |

Better Auth needs the same discipline. Its `getMigrations()` reports only `toBeCreated` tables and `toBeAdded` columns ([Better Auth database](https://www.better-auth.com/docs/concepts/database)). That looks additive, but it runs outside Skiff's numbered migrations and outside any linter. The robust fix is to generate Better Auth's SQL into numbered migration files at development time. At boot, readiness should fail if Better Auth's diff is non-empty, so one runner owns the schema. Schema versioning should combine `PRAGMA user_version`, a cheap integer in the header that is atomic with the migration transaction and that "SQLite makes no use of" ([SQLite PRAGMA](https://www.sqlite.org/pragma.html)), with a `schema_migrations` table for names and checksums. Each release should then declare the *range* of schema generations it tolerates. Forgejo-style "refuse if newer" would forbid the very rollback Skiff wants. Litestream point-in-time restore is disaster recovery, not rollback. It restores whole LTX files, "not every transaction is a valid restore point", and it still loses post-switch writes ([Litestream restore](https://litestream.io/reference/restore/)).

No product surveyed documents a CI gate that runs the N-1 binary against the new schema. This report infers it from GitLab's rules rather than citing it, and it is cheap for Skiff because both binaries and the database are local files. CI checks out the previous tag, builds it, and runs its integration suite against a database migrated by HEAD. It then runs HEAD's suite against that database after N-1 has written to it. This catches both "old code inserts NULL into a new NOT NULL column" and "new code chokes on rows old code wrote".

## Recommended architecture: a stage-0 supervisor that never ships with the payload

The design splits responsibility along the line every robust updater draws. A **stage-0 updater** owns generic mechanism: fetch, verify, unpack, call hooks with timeouts, flip pointers, arm and clear the trial, revert. It knows nothing about Skiff's data layout. Each **release** owns knowledge of itself: how to prepare its sandbox, migrate, self-check and report readiness. A bug in a release's hooks can then fail only that release, because the next release ships its own fixed hooks. A bug in stage-0 is contained by stage-0's own qualification gate and by an out-of-band recovery path. This is the layering behind ONCE's separate `once self-update` and app-update code paths ([ONCE self_update.go](https://github.com/basecamp/once/blob/main/internal/command/self_update.go)), HAOS's RAUC-versus-Supervisor split ([HA OS update system](https://contributors.home-assistant.io/os/operating-system/update-system/)), and Chromium's side-by-side updater instances, which "perform a self-test before activating" ([Chromium updater design](https://chromium.googlesource.com/chromium/src/+/main/docs/updater/design_doc.md)).

### Layout and components

```
/usr/local/lib/skiff-updater/<u-ver>/skiff-updated   stage-0: compiled single binary, own embedded runtime, root
/usr/local/lib/skiff-updater/current -> <u-ver>      stage-0 pointer (flipped only after qualification)
/usr/local/sbin/skiff-update-self -> .../current/skiff-updated
/usr/local/sbin/skiff-recover                        out-of-band tool, also a release asset; no dependency on stage-0 logic
/etc/skiff/updater/keys.json                         offline root pubkeys + root-signed list of signing keys
/opt/skiff/releases/<ver>-<sha12>/                   root-owned, read-only after verify; control-plane, agent, helper, cli,
                                                     bin/skiff-release (hooks), release.json (schema range, min_updater, hook protocol)
/opt/skiff/current, /opt/skiff/previous              committed pointers (what boots after a reboot)
/var/lib/skiff-update/trial.json                     {version, colour, phase, attempts_left, deadline}, armed before cutover
/var/lib/skiff-update/verdicts.json                  per-version verdict + attributed cause (replaces update-state.json skip list)
skiff-control-plane@{blue,green}.service             template unit; socket /run/skiff/control-<colour>.sock
skiff-update-guard.service                           ordered Before= both colours at boot; reverts any uncommitted trial
```

Stage-0 must not run on the release's Bun or `node_modules`. It should be a self-contained compiled binary, released on its own slower cadence and listed as a separate artifact in the manifest. It should stay small enough to review whole. Release hooks speak a versioned JSON protocol (`skiff-release prepare|rehearse|migrate --pre|migrate --post|selfcheck`), each with a hard timeout and structured output: `{ok, step, reason, detail}`. New protocol features are opt-in, following RAUC's rule that older installers must still handle newer bundles ([RAUC](https://rauc.readthedocs.io/en/latest/basic.html)). If a release's `min_updater` is newer than the installed stage-0, stage-0 updates itself first. The incident bug moves into `prepare`, and so does any mkdir or chown that encodes Skiff's data layout. Better still, data directories should be declared through systemd `StateDirectory=` or `tmpfiles.d` rather than created imperatively, so ownership is right by construction in production, the canary and CI alike. `skiff-update-guard.service` plays the bootloader: it runs at boot before either colour starts. If `trial.json` shows an uncommitted trial, it decrements `attempts_left`, and at zero it restores `current` to `previous` and re-asserts the Caddy upstream. A power cut mid-update therefore converges on the last committed release with no updater running.

### The update state machine

| Phase | Action | On failure | Blame |
|---|---|---|---|
| Resolve | Fetch the signed manifest; check serial ≥ last seen, expiry, channel, `rollout_percent`, `min_upgrade_from` (chain through required stops) | Retry with backoff | Environment |
| Fetch and verify | Download the artifact; check sha256 against the manifest and the signature against the key chain | Retry; never touches `current` | Environment |
| Unpack | Write `releases/<v>` to a temp dir, `rename` into place, make it read-only | Delete the partial dir | Environment / stage-0 |
| Rehearse | New release's `rehearse` on a `VACUUM INTO` copy: pre migrations in one transaction, `integrity_check` plus `foreign_key_check`, boot N on the copy in the production sandbox, then boot **N-1 on the migrated copy** | Discard the copy | **Release** (only if the hook returned a well-formed verdict) |
| Migrate | New release's `migrate --pre` on the live DB under `BEGIN IMMEDIATE`; blue keeps serving, and writes wait briefly on the lock | The transaction rolls back and the DB is untouched | Release |
| Start green | Start `@green` with singletons disabled; wait for deep readiness and smoke requests straight to `control-green.sock` | Stop green; blue never stopped serving | Release |
| Cutover | Arm `trial.json`, then `PATCH /id/skiff_cp/upstreams` with `If-Match` | PATCH back; Caddy keeps the old config if the new one is invalid | Stage-0 |
| Bake | 60–120 s with blue idle but running: watch green's 5xx ratio, restarts, readiness flaps, and `selfcheck` (including "can I be updated", i.e. hook protocol and trigger path) | PATCH back to blue, stop green; **code-only revert, no DB restore** | Release |
| Commit | Flip `current`/`previous`, transfer leases, stop blue, clear the trial, restart the helper and agent, mark the verdict good | Not reversible by design; the next update is the fix | n/a |
| Post | Run pending post (contract) migrations from *earlier* committed releases | Stays pending, retried next time | Release |

Snapshot restore remains, but only as an explicit operator action, or automatically when N-1 itself fails readiness on the migrated schema. With rehearsal in place that case should be nearly impossible. Before any restore, the dashboard states the size of the data-loss window. The helper and agent are host-wide and shared across colours, the "static kernel" risk from the Hackaday case. They must accept both N-1 and N control-plane clients through a versioned protocol, and they restart only at commit.

### Failure attribution and the blocklist

Most of the liveness guarantee comes from this rule set. A version is marked bad only when a **release-owned hook returned a well-formed failure verdict**, or when green failed the bake. Network, disk, signature, timeout-before-hook, and any stage-0 exception count as environment or updater failures: they retry with backoff and never blocklist. If two consecutive *distinct* releases fail at the same phase with the same reason, stage-0 stops marking versions bad. It then raises an "updater suspected" alert with the hook's actual `reason`, which in the incident would have been the `/readyz` body rather than systemd's "Starting skiff-update-canary-…" line. That heuristic is this report's inference, not a cited practice. A bad verdict never blocks a version newer than the bad one. The signed manifest can revoke a version (the kill switch) or clear a verdict. Every rejection carries a human-readable cause in the dashboard. Without those rules, as the research notes put it, "record failed commit and skip it" is safe only if failure attribution is correct.

### Updating the updater, and the escape hatch

Stage-0 updates itself the Chromium way. The new instance installs side by side as unqualified, then qualifies by running a full dry run against the currently installed release: verify, rehearse on a copy, start and stop a throwaway green on a scratch socket, with no cutover. Only after that does it flip `/usr/local/lib/skiff-updater/current`. A failed qualification leaves the old stage-0 active and reports upstream ([Chromium updater design](https://chromium.googlesource.com/chromium/src/+/main/docs/updater/design_doc.md)). Stage-0 and the app are never updated in the same transaction. For the case where every layer fails, `skiff-recover` mirrors Home Assistant's `update-supervisor.txt` and Coolify's terminal `upgrade.sh <version>` ([Coolify downgrade](https://coolify.io/docs/core/instance-management/downgrade)). It can list releases, point `current` at any one, re-assert the Caddy upstream, install a stage-0 or release from a local file with signature check, and clear verdicts. It is published as a release asset, so a single `curl … | sh -s <version>` works even when nothing on the host can update.

## Phased migration from today's updater

The order is set by risk. The liveness trap is the live problem, so stage-0 comes first. Prebuilt artifacts remove the largest class of host-specific failures. Migration discipline has to land *before* blue/green, because two colours sharing one database are only safe once N-1 tolerates schema N.

| Phase | Goal | Work | Exit criterion |
|---|---|---|---|
| 0: Unblock (now) | Land the chown fix without trusting the broken installed updater | As root on the host, run the *fixed* `scripts/update-self/main.ts` from a fresh checkout of the fix commit using the pinned `runtime/bun`, targeting that commit with `--force`. This is the out-of-band path. Then clear the 0.6.2 and 0.6.3 entries from `/opt/skiff/update-state.json`. In the same release, show the last `/readyz` body as the canary failure reason, and stop blocklisting when the canary fails before the candidate's code serves a request | Host on the fixed release; the next normal release passes the canary unaided |
| 1: Split stage-0 | An updater bug can no longer veto releases | Extract fetch/verify/unpack/flip/trial/revert into a compiled `skiff-updated` under `/usr/local/lib/skiff-updater/`, and repoint `/usr/local/sbin/skiff-update-self` at it. Move canary preparation and checks behind `skiff-release` hooks inside each release. Add `trial.json`, `skiff-update-guard.service`, verdict attribution, `skiff-recover`, and Chromium-style stage-0 qualification. Declare data dirs with `StateDirectory=`/`tmpfiles.d` | CI fault-injection: `kill -9` stage-0 at every phase on a VM converges on the last committed release; a deliberately broken release hook fails only that release |
| 2: Ship artifacts | No compilation on the host; every payload verified | A CI release job builds a tarball (`build/`, prod `node_modules`, pinned Bun, agent, CLI, helper) with fixed ownership and modes. A signed manifest (serial, expiry, channel, sha256, `min_updater`, `min_upgrade_from`, schema range, revocations) uses an offline root key and a CI signing key. CI runs the host's own canary under the production sandbox against N-1, N-2 and baseline fixture DBs. Optional attestations. Evaluate `adapter-bun` `compile: true` with DuckDB external | Host update has no `bun install`/`vite build`; update peak memory drops from 3.2 GB to roughly the size of the unpack |
| 3: Migration discipline | Rollback becomes code-only and lossless | Split migrations into `pre/` and `post/`. Add a preflight linter using the Atlas BC/DS/MF classes plus the SQLite rules above, with unparseable SQL treated as unsafe. Add `user_version` plus `schema_migrations` with checksums and per-release schema-tolerance ranges. Generate Better Auth SQL into numbered files and fail readiness on a non-empty Better Auth diff. Add the N-1-on-new-schema CI gate. Switch default rollback from snapshot restore to code-only | A rollback drill on staging loses zero writes; a contract migration in a pre file fails CI |
| 4: Blue/green | Updates with no visible downtime | Add template units `skiff-control-plane@{blue,green}` and per-colour sockets. Give the Caddy `reverse_proxy` an `@id`, with stage-0 owning the upstream and re-asserting it at boot. Set `stream_close_delay` on control-plane and app routes, and `lb_try_duration` as a fence. Add `busy_timeout`/`BEGIN IMMEDIATE` everywhere, a lease table for singletons with promotion-gated start, a 60–120 s bake with PATCH-back, and versioned helper/agent protocols | Synthetic load during an update sees zero 5xx and zero refused connections; a forced bake failure reverts in under 2 s |
| 5: Continuous assurance | Rollback stays trustworthy over time | A scheduled update-and-rollback drill on the host, alongside the existing `skiff-restore-drill.service`. Channels (stable/beta), `rollout_percent` buckets once several installations exist, and declared upgrade stops when migrations get heavy ([GitLab upgrade paths](https://docs.gitlab.com/update/upgrade_paths/)) | Drill results visible in the dashboard; a failed drill blocks promotion to stable |

Several facts remain unverified and should be checked at the phase that depends on them. Phase 4: whether Bun can emit sd_notify readiness, and whether a future Bun gains fd-listen support. Phase 3: which SQLite version Bun bundles, which decides whether 3.53's `ALTER COLUMN` is available. Phase 2: whether DuckDB's native bindings package cleanly beside a compiled executable. Phase 4 again: whether Skiff's Caddy runs from a Caddyfile or persisted JSON, which decides how stage-0 makes the upstream survive a Caddy restart (`persist_config` and `--resume` exist for the JSON route ([Caddy API](https://caddyserver.com/docs/api))).

## Conclusion

The incident changes what "failsafe" has to mean for Skiff. The existing design already had most of what the update literature calls safety: immutable release directories, an atomic symlink flip, a kept `previous`, and a sandboxed canary. What it lacked was liveness, and liveness turns out to depend less on how careful the checks are than on *who owns them* and *how far their verdicts are trusted*. Checks owned by the outgoing release, combined with a blocklist that believes every failure, make any updater bug permanent. Checks owned by the incoming release, run by a minimal arbiter that blames itself before it blames a release, make the same bug cost one release at most.

Two second-order points follow. First, blue/green and expand-only migrations depend on each other: two colours on one SQLite file are only as safe as N-1's tolerance for schema N, which is why Phase 3 has to come before Phase 4. Second, the rollback path is the least exercised code in any updater and the most important. Skiff already drills restores on a schedule, and the same treatment should extend to update-and-rollback, with fault injection at every state-machine phase in CI. Under this design no single bug can strand the host, and the dashboard says plainly which part failed and why.
