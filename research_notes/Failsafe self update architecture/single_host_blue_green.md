# Single-host blue/green and health-gated cutover (Skiff control plane: Bun + unix socket + systemd + Caddy + SQLite/Litestream)

Research date: 2026-11-05. Sources are primary docs or source code unless marked otherwise. kamal-proxy defaults come from its Go source at tag ~v0.10.2. Caddy docs were read in current form (v2.11-era).

## How do Kamal 2 / kamal-proxy, Dokku, Coolify and CapRover implement zero-downtime deploys (health checks, draining, rollback, pausing)?

### Takeaway
They all use the same pattern. Boot the new instance next to the old one, poll a health endpoint until it passes or a deadline expires, switch the proxy's target in one step, then drain the old instance for a bounded time and stop it. Rollback means re-pointing the proxy at the previous instance, which was kept, not rebuilt. kamal-proxy adds a "pause" primitive that holds requests in the proxy for up to 30 s. This is the closest industry analogue to a short, safe write fence. Every PaaS surveyed weakens or turns off zero-downtime when the app has a persistent volume. That is exactly Skiff's SQLite case, although on one host both processes can share the disk.

### Cited Findings
**kamal-proxy (Basecamp, Go):**
- Deploy semantics: `kamal-proxy deploy service1 --target web-1:3000`. Health checks start straight away. Traffic moves only after they pass, and the new instance takes over all traffic from the previous one. "The `deploy` command also waits for traffic to drain from the old instance before returning." If the instance isn't healthy in time, deploy stops with a non-zero exit code — [kamal-proxy README](https://github.com/basecamp/kamal-proxy)
- Defaults in the source (`internal/server/service.go`): `DefaultDeployTimeout = 30s`, `DefaultDrainTimeout = 30s`, `DefaultPauseTimeout = 30s`, `DefaultHealthCheckPath = "/up"`, `DefaultHealthCheckInterval = 1s`, `DefaultHealthCheckTimeout = 5s`, `DefaultTargetTimeout = 30s`, `DefaultMaxMemoryBufferSize = 1MB` — [kamal-proxy source, service.go](https://github.com/basecamp/kamal-proxy/blob/main/internal/server/service.go)
- Deploy flags: `--deploy-timeout` ("Maximum time to wait for the new target to become healthy"), `--drain-timeout` ("Maximum time to allow existing connections to drain before removing old target"), `--force` ("Skip health checks and force deployment"), `--health-check-path/-interval/-timeout/-port/-host`, `--buffer-requests`, `--buffer-responses`, `--target-timeout`. There is also `--read-target` with `--writer-affinity-timeout` (default 1 s), which routes reads to read-only replicas until shortly after a write — [kamal-proxy source, cmd/deploy.go](https://github.com/basecamp/kamal-proxy/blob/main/internal/cmd/deploy.go)
- Pause/stop/resume. `kamal-proxy pause <service>` takes `--drain-timeout` ("How long to allow in-flight requests to complete") and `--max-pause` ("How long to enqueue requests before shedding load", default 30 s). `stop` takes `--drain-timeout` and `--message` ("Message to display to clients while stopped"). `resume` returns the service to normal — [kamal-proxy source, cmd/pause.go & stop.go](https://github.com/basecamp/kamal-proxy/tree/main/internal/cmd)
- Pause behaviour, from a third-party analysis of the code: paused services block new requests and return 504 after the max-pause timeout, while in-flight requests finish within the drain timeout. Stopped services return 503 with the custom message — [DeepWiki kamal-proxy lifecycle (auto-generated, secondary)](https://deepwiki.com/basecamp/kamal-proxy/3.2-service-lifecycle-management)
- Rollout/canary: `kamal-proxy rollout deploy`, `rollout set --percent N` / `--list <values>` ("Rollout to specific values"), and `rollout stop` — [kamal-proxy source, cmd/rollout_set.go](https://github.com/basecamp/kamal-proxy/tree/main/internal/cmd). Per secondary analysis, the split is sticky via a `kamal-rollout` cookie and persists across proxy restarts — [DeepWiki deployment & rollouts](https://deepwiki.com/basecamp/kamal-proxy/3.1-deployment-and-rollouts)
- kamal-proxy persists its routing state to a state file and restores it at startup (`RestoreLastSavedState`, `saveStateSnapshot`), so a proxy restart doesn't lose the active target — [kamal-proxy source, router.go](https://github.com/basecamp/kamal-proxy/blob/main/internal/server/router.go)
- Kamal config: health check defaults are `/up`, polled "once every second until we hit the deploy timeout", with a 5 s per-request timeout. `response_timeout` defaults to 30 s. Buffering is on by default (1 GB max request body, no response limit, 1 MB memory then disk) — [Kamal proxy config docs](https://kamal-deploy.org/docs/configuration/proxy/)
- Kamal rollback, `kamal rollback VERSION`: if the old version is still available as a container (`container_available?`), Kamal re-boots it through the normal `app:boot` path, which goes through kamal-proxy's health-gated deploy again. Otherwise it fails with "not available as a container" — [Kamal source, cli/main.rb](https://github.com/basecamp/kamal/blob/main/lib/kamal/cli/main.rb)

**Dokku:**
- Each new container waits `default-wait` (10 s) unless checks are defined. After all new containers start, traffic switches. Old containers get SIGTERM straight after the switch. They are kept for `wait-to-retire` (default 60 s), then stopped (SIGTERM, then SIGKILL after `stop-timeout-seconds`, default 30) — [Dokku zero-downtime docs](https://dokku.com/docs/deployment/zero-downtime-deploys/)
- `app.json` healthchecks have `type` startup/liveness/readiness, plus `path` (default `/`), `attempts` (3), `wait` (5), `timeout` (5) and `initialDelay` (0). With nginx, traffic goes to new containers only after checks pass. Caddy, openresty and traefik route to a container "once it is running", and the first readiness check is translated into proxy health checks. `checks:disable` stops old containers before starting new ones, which causes downtime — [Dokku zero-downtime docs](https://dokku.com/docs/deployment/zero-downtime-deploys/)

**Coolify:**
- Rolling updates start the replacement container without stopping the current one, then wait for its health check if one is configured. Without a health check, a started container counts as ready. The docs state that rolling updates do not guarantee zero downtime unless the app cooperates. Not supported for Docker Compose apps — [Coolify rolling updates docs](https://coolify.io/docs/applications/deployments/rolling-updates); [Coolify health checks](https://coolify.io/docs/applications/configuration/health-checks)

**CapRover:**
- Apps without volumes use Docker Swarm `start-first` updates, so the new container runs before the old one is killed and Swarm waits for the HEALTHCHECK before routing. Apps with persistent volumes use `stop-first`, which causes downtime — [CapRover zero-downtime docs](https://caprover.com/docs/zero-downtime.html)

**Volumes break zero-downtime elsewhere too:**
- Render: "Attaching a persistent disk" turns off zero-downtime deploys. Otherwise Render waits 60 s after the new instance takes traffic, sends SIGTERM to the old one, then SIGKILL after 30 s (configurable up to 300 s, `maxShutdownDelaySeconds`, but not customisable for disk services) — [Render deploys docs](https://render.com/docs/deploys)

### Inferences
- kamal-proxy's model maps almost one-to-one onto Caddy plus a small Skiff-side orchestrator: deploy = health-poll the new socket, then PATCH the upstream; drain = wait N s, then SIGTERM the old unit; pause = hold requests in Caddy with `lb_try_duration` (see Q2).
- I found no unix-socket target support in kamal-proxy. A grep of `target.go` for "unix" and "socket" returned nothing. Adopting kamal-proxy itself would mean replacing Caddy (and its TLS) or chaining proxies, so it is better used as a reference design.
- Platforms turn off zero-downtime for volumes because a volume can be attached to only one machine or container. On a single host, blue and green can both open the same SQLite file, so this constraint does not apply directly. The real constraint is schema compatibility and singleton work (Q4, Q5).

### Gaps
- Official kamal-proxy README wording on pause/resume was not visible on the fetched page. Flag semantics come from source, and the runtime 504/503 behaviour from a secondary (DeepWiki) source.
- No current Kamal docs page confirmed `retain_containers` defaults for how many old versions are kept for rollback.

## Caddy specifics: atomic upstream switching via admin API, health checks, holding requests during a switch, in-flight requests and websockets on reload

### Takeaway
Caddy can be the blue/green switch. Give the `reverse_proxy` handler an `@id`, then `PATCH /id/<id>/upstreams` to `[{"dial":"unix//run/skiff/control-green.sock"}]`. Each admin-API change is a full, graceful config reload that rolls back automatically if invalid. Normal HTTP requests in flight finish under an "eternal" default `grace_period`. WebSockets and other streams are force-closed on every reload unless `stream_close_delay` is set. `lb_try_duration` / `lb_try_interval` let Caddy hold and retry requests while no upstream is reachable, which gives a kamal-style "pause".

### Cited Findings
- Admin API: "Configuration changes are lightweight, efficient, and incur zero downtime." "If the new config fails for any reason, the old config is rolled back into place without downtime." If the new config is identical, no reload occurs — [Caddy API docs](https://caddyserver.com/docs/api)
- Path editing: "PATCH strictly replaces an existing value or array element". POST appends to arrays. PUT inserts or strictly creates. Any object can get an `"@id"` and be addressed via `/id/<name>/...` "in the same way you would to the corresponding `/config/` endpoint" — [Caddy API docs](https://caddyserver.com/docs/api)
- Concurrency control (marked experimental): use `Etag` / `If-Match`. On HTTP 412, re-read and retry — [Caddy API docs](https://caddyserver.com/docs/api)
- Persistence: the latest config is autosaved after changes, and `caddy run --resume` restarts with the last working config. `persist_config off` disables this. The admin endpoint can be bound to a unix socket (`admin unix//path`) so file permissions control access — [Caddy API docs](https://caddyserver.com/docs/api); [Caddy global options](https://caddyserver.com/docs/caddyfile/options)
- `grace_period`: during shutdown or reload of old servers, "no new connections are accepted, idle connections are closed, and active connections are impatiently waited upon". Default: "the grace period is eternal, which means connections are never forcefully closed". `shutdown_delay` keeps the old server running normally (with `{http.shutting_down}` = true) before the grace period — [Caddy global options](https://caddyserver.com/docs/caddyfile/options)
- WebSockets/streams: "By default, WebSocket connections are forcibly closed when the config is reloaded." `stream_close_delay` delays closing streams on config unload (default: no delay). `stream_timeout` closes streams after a timeout (default none) — [Caddy reverse_proxy docs](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)
- A real-world report (Caddy v2.11, June 2026): each `PATCH` to a map triggered a reload and broke a WebSocket. Setting `stream_close_delay` fixed it. A community responder noted that "For normal HTTP requests Caddy config reloads are graceful" and that reloads are "not for high-churn routing data" — [Caddy community thread](https://caddy.community/t/way-to-achieve-zero-downtime-for-existing-connections-when-dynamic-patch-maps/33753)
- Holding or retrying requests: `lb_try_duration` is "how long to try selecting available backends for each request if the next available host is down" (default 0, disabled). `lb_try_interval` defaults to 250 ms. `lb_retries` gives a count instead. `lb_retry_match`: by default only GET requests are retried, but a retry is always allowed if the connection to the upstream failed — [Caddy reverse_proxy docs](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)
- Active health checks: enabled by `health_uri` or `health_port`. Defaults are `health_interval 30s`, `health_timeout 5s`, `health_status 200` (or class like `2xx`), `health_passes 1` and `health_fails 1`. Passive checks: `fail_duration` > 0 enables them (default 0, off), plus `max_fails` (default 1) and `unhealthy_status` — [Caddy reverse_proxy docs](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)
- `lb_policy first` "chooses the first available upstream, from the order they are defined". The docs warn to enable health checks with it, "otherwise failover will not occur" — [Caddy reverse_proxy docs](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)
- Unix socket upstreams use a network prefix: `unix//var/php.sock`, `unix+h2c//...`. For HTTPS over a socket the Host header must be set explicitly — [Caddy reverse_proxy docs](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)
- Dynamic upstreams (`dynamic a`, `dynamic srv`, `dynamic multi`) resolve via DNS with a 1 m default refresh — [Caddy reverse_proxy docs](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)

### Inferences
- Recommended Caddy switch for Skiff: one `reverse_proxy` with `"@id": "skiff_cp"` and a single upstream. Cutover is `PATCH /id/skiff_cp/upstreams` with `If-Match`, done only after Skiff's orchestrator has health-checked the new socket directly (curl `--unix-socket`). This is atomic from the proxy's point of view: the old config serves until the new one is in place. Rollback is the same PATCH back, as long as the old process is still running.
- The two-upstream alternative is to list both sockets with `lb_policy first` and active health checks. Failover then happens without API calls, but it is driven by health checks (up to `health_interval` latency) rather than an explicit cutover, and it can flap. The single-upstream PATCH approach is more deterministic.
- `lb_try_duration 5s`–`30s` combined with an upstream that is briefly unreachable acts like kamal-proxy `pause`: Caddy keeps retrying each request until the new socket accepts or the duration expires. This also covers the current stop/start path's few-second gap. POSTs are retried only when the dial fails, which is the safe case.
- Long-lived connections (SSE/WebSocket dashboards) will drop on every admin-API change unless `stream_close_delay` is set. Clients should reconnect anyway. A long delay keeps old-generation stream goroutines (and the old upstream) alive, so the old Bun process should not be killed while streams it serves are still open.
- Every PATCH reloads the whole config, so other sites served by the same Caddy (Skiff-managed apps) also go through a graceful reload. This is fine for HTTP but drops their WebSockets too, unless `stream_close_delay` is set on those routes as well.

### Gaps
- No maintainer-confirmed statement on the memory cost of a long `stream_close_delay`.
- Whether Caddy can add or remove a single upstream without a full reload: no source found. Docs imply every admin change is a config reload.

## Process-level handoff alternatives (systemd socket activation / FD store, nginx USR2, HAProxy seamless reload, Envoy hot restart, tableflip): which work for a Bun server on a unix socket?

### Takeaway
All of these hand a *listening socket* from the old process to the new one, so no connection is refused. Except for tableflip (Ready() gating) and nginx (manual rollback), they do not health-gate the new code before it takes traffic. Bun does not currently document listening on an inherited file descriptor. A Bun.serve `{fd}` PR was closed unmerged, so systemd socket activation is not directly usable without a proxy shim. For Bun on a unix socket, proxy-level blue/green (two sockets, Caddy switch) is the practical route. Socket-handoff techniques are at best a fallback for queueing connections during a restart.

### Cited Findings
- systemd socket activation: listening sockets stay owned by systemd, so "you can kill a daemon but you won't lose a single connection" — [Poettering, Fedora devel list 2010](https://lists.fedoraproject.org/pipermail/devel/2010-July/139384.html). While the service restarts, new connections wait in the listen queue (size from `Backlog=`). On overflow they are dropped — [Vincent Bernat, systemd socket activation for Go](https://vincent.bernat.ch/en/blog/2018-systemd-golang-socket-activation). Restarting the *socket unit* itself always leaves a brief gap — [systemd-devel 2021](https://lists.freedesktop.org/archives/systemd-devel/2021-July/046723.html)
- `FileDescriptorStoreMax=` (systemd 219+): "Any open sockets and other file descriptors which should not be closed during the restart may be stored this way." `FileDescriptorStorePreserve=` (254+) controls when the store is released (`no`, `yes`, `restart`, `on-success`). `RestartMode=direct` (254+). `Type=notify` expects `READY=1`, and `Type=notify-reload` is recommended over async signal reloads — [systemd.service(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html)
- Passed sockets start at fd 3 (`SD_LISTEN_FDS_START`). `LISTEN_FDS` is a count, and `LISTEN_PID` must match — [sd_listen_fds(3)](https://www.unix.com/man-page/linux/3/SD_LISTEN_FDS)
- Bun: PR #2852 (May 2023) proposed `Bun.serve({fd})` / `Bun.listen({fd})` for systemd socket activation and zero-downtime deploys, noting `socat` or `systemd-socket-proxyd` as workarounds. It is closed. The uSockets prerequisite (PR #192) was left with conflicts in May 2024. No merged fd-listen option was found in 2026 changelogs — [Bun PR #2852 mirror](https://gh.r-mj.com/oven-sh/bun/pull/2852); [uSockets PR #192 mirror](https://gh.r-mj.com/uNetworking/uSockets/pull/192); [Bun changelog digest Apr 2026](https://kt3k.github.io/changelog/oven-sh/bun/2026/04)
- nginx binary upgrade: replace the binary, send `USR2` to the master (a new master plus workers start alongside the old), `WINCH` to the old master so its workers drain, then `QUIT` to the old master. Rollback: send `HUP` to the old master to respawn workers, then `QUIT` the new master — [freenginx control docs](https://freenginx.org/en/docs/control.html); [Tengine mirror of nginx docs](https://tengine.taobao.org/nginx_docs/cn/docs/control.html). A July 2024 report found that sending WINCH and QUIT back to back could leave no new workers. The advice is to wait for the new PID file before signalling — [nginx mailing list 2024](https://mailman.nginx.org/pipermail/nginx/2024-July/WFWXHEIYGJ7BPHXOBDK6VVOLHTRTBXVV.html)
- HAProxy: hitless reloads since 1.8 pass listening sockets from old to new process. In master-worker mode the master transfers sockets over its internal socketpair, so `-x` / `expose-fd listeners` is no longer needed. A third-party article contradicts this — [HAProxy blog, truly seamless reloads](https://www.haproxy.com/blog/truly-seamless-reloads-with-haproxy-no-more-hacks); [HAProxy commit](https://git01.mediatek.com/plugins/gitiles/haproxy/+/2be557f7cb566e4fa8e3ea5a332e69698adc36c4%5E%21); contradicted by [StackHarbor](https://stackharbor.com/en/knowledge-base/haproxy-hot-reload/)
- Envoy hot restart: stats and locks live in shared memory. The new process takes the listen sockets, then the old one drains for `--drain-time-s`. After `--parent-shutdown-time-s` it is told to exit. The two communicate only over unix domain sockets. By default there is one active plus one draining process per host. Not supported on Windows — [Envoy hot restart docs v1.17](https://envoyproxy.io/docs/envoy/v1.17.2/intro/arch_overview/operations/hot_restart)
- Cloudflare tableflip (Go): `Upgrade()` re-execs argv[0], passing listening fds. The new process calls `Ready()` when initialised, and only then does the old one exit. A crash during init is tolerated, and only one upgrade runs at a time. Linux and macOS only. Latest tag is v1.2.3 (Mar 2022), so it is stable but dormant — [tableflip GitHub](https://github.com/cloudflare/tableflip); [pkg.go.dev](https://pkg.go.dev/github.com/cloudflare/tableflip); [Cloudflare blog](https://blog.cloudflare.com/graceful-upgrades-in-go/)

### Inferences
- For Bun on `/run/skiff/control.sock`, socket handoff would need either fd-listen support in Bun (unconfirmed, absent as of research) or a shim such as `systemd-socket-proxyd`, which is itself a proxy. Since Caddy is already a proxy, adding another buys nothing.
- Even where handoff works, it serialises old and new. The new process doesn't get proven before it owns the listener, unless it uses a tableflip-style `Ready()` with the old process still accepting. That gives "no refused connections", not "can't fail".
- Unix-socket blue/green needs distinct paths per colour (e.g. `control-blue.sock` / `control-green.sock`), because two processes cannot bind the same path at once. The Caddy upstream PATCH is then the switch. One alternative is binding the new socket to a temp path and atomically `rename(2)`-ing it over `control.sock`. This is unverified here: no source was fetched on rename semantics for bound sockets. It would also make rollback harder, so it is not recommended.
- systemd template units (`skiff-control-plane@blue.service` / `@green.service`), each with its own socket path and `Type=notify` readiness, fit the two-colour model cleanly.

### Gaps
- Bun's official docs were not fetched to confirm the absence of `fd` / `reusePort`-style options for unix sockets in the current Bun release. Treat "no fd-listen" as likely, not certain.
- No authoritative source on whether `systemd-socket-proxyd` preserves request continuity across backend restarts.

## Two versions sharing one SQLite database: WAL concurrency, single writer, busy_timeout, migrated-schema danger, write fences; Litestream with two writers or during restart

### Takeaway
Two processes on the same host can safely share one WAL-mode SQLite file. Readers don't block writers, but there is exactly one writer at a time, so both processes need `busy_timeout` and should use `BEGIN IMMEDIATE` for write transactions. SQLite handles the overlap itself. The real hazards are elsewhere: old code running against a migrated schema, and running two Litestream replicators. The industry answer for schema is expand/contract (backwards-compatible migrations, with contract steps deferred to a later release). Where a breaking migration is unavoidable, the practical answer is a short proxy-level "pause" (hold requests, drain old, migrate, start new) rather than downtime. Litestream is a separate process, so app restarts or blue/green overlap don't disturb it, provided only *one* Litestream instance replicates the DB.

### Cited Findings
- WAL: "readers do not block writers and a writer does not block readers". However, "since there is only one WAL file, there can only be one writer at a time". "All processes using a database must be on the same host computer" (shared-memory wal-index) — [SQLite WAL](https://www.sqlite.org/wal.html)
- SQLITE_BUSY can still occur in WAL mode: when another connection holds exclusive locking mode, when the last connection is closing and cleaning up the WAL/shm, or during crash recovery — [SQLite WAL §9](https://www.sqlite.org/wal.html)
- Checkpoint starvation: if there is always at least one active reader, "no checkpoints will be able to complete and hence the WAL file will grow without bound" — [SQLite WAL §6](https://www.sqlite.org/wal.html)
- The WAL is part of persistent state. "The only safe way to remove a WAL file is to open the database file ... and then immediately close". The last connection to close checkpoints and deletes the WAL — [SQLite WAL §4, §6](https://www.sqlite.org/wal.html)
- With DEFERRED transactions, a read transaction that later writes will "upgrade ... if possible, or return SQLITE_BUSY" if another connection has written meanwhile. `BEGIN IMMEDIATE` takes the write lock up front. IMMEDIATE and EXCLUSIVE are the same in WAL mode — [SQLite transactions](https://www.sqlite.org/lang_transaction.html)
- Litestream: "SQLite is built to run as a multi-process embedded database and Litestream acts as just another process". Apps must set `PRAGMA busy_timeout = 5000`. Litestream works only in WAL mode. Apps should run with `PRAGMA wal_autocheckpoint = 0`, because app checkpoints under heavy load can make Litestream miss WAL frames, forcing a full snapshot. "It is _your_ responsibility to ensure you do not have multiple applications replicating concurrently" — [Litestream tips](https://litestream.io/tips/)
- Two Litestream instances on one node replicating the same DB caused a flood of problems, which the maintainer attributed to long-running read transactions — [Litestream issue #422](https://www.github.com/benbjohnson/litestream/issues/422)
- Litestream "revamped" (0.5 line, 2025) uses object-store conditional writes for a time-based lease, so nodes with overlapping run times can share a destination without confusing each other — [Fly.io blog, Litestream: Revamped](https://fly.io/blog/litestream-revamped/). Per an HN comment quoting the docs (secondary), a new process that finds an existing lease retries every second — [HN](https://hn.nuxt.dev/item/44045292)
- Expand/contract (parallel change): during rolling or blue/green deploys the schema must support old and new code at once. Expand (add), migrate (backfill / dual-write), contract (remove), with contract deferred, possibly to a later release. GitLab's multi-version compatibility guide treats this as a requirement for zero-downtime on-prem upgrades — [GitLab multi_version_compatibility (mirror)](https://git.causa-arcana.com/kotovalexarian-likes-gitlab/gitlab-org--gitlab-foss/blame/commit/b0980f5557a8621fb08785b06be950ee46796c18/doc/development/multi_version_compatibility.md); [DevOpsDays talk](https://devopsdays.org/events/2019-seattle/program/leena-s-n/)
- Write fence in practice: kamal-proxy's `pause` ("How long to enqueue requests before shedding load", 30 s default) exists for maintenance operations that need traffic held briefly — [kamal-proxy cmd/pause.go](https://github.com/basecamp/kamal-proxy/tree/main/internal/cmd). Render and CapRover simply drop to stop-first, with downtime, when persistent storage is involved — [Render](https://render.com/docs/deploys); [CapRover](https://caprover.com/docs/zero-downtime.html)

### Inferences
- Recommended rule for Skiff: every migration shipped in release N must be safe for release N-1 code to run against (additive only: new tables, nullable or defaulted columns, new indexes). Destructive changes (drop/rename column, tighter constraints) wait until release N+1, once N-1 can no longer be rolled back to. This is what makes "instant revert" honest. Rolling back the binary must not require rolling back the schema.
- Migrations should run in the *new* process before it reports ready, or in a pre-flight step, inside one `BEGIN IMMEDIATE` transaction with `busy_timeout`. Old blue keeps serving reads during this, and its writes briefly wait on the lock.
- For an occasional unavoidable breaking migration, use a fence. Set Caddy's upstream to a not-yet-listening green socket with `lb_try_duration` around 30 s (requests are held). SIGTERM blue and wait for its drain, run the migration in green, then green listens and held requests flow. Users see added latency, not errors, if the whole sequence fits inside `lb_try_duration`. The more principled variant is an app-level `maintenance` flag in SQLite that makes the old version reject or queue writes (503 + Retry-After) while still serving reads.
- Litestream should be one long-lived systemd unit independent of the blue and green units, so overlap doesn't affect replication. Never start a second Litestream (e.g. `litestream replicate -exec` per colour) against the same DB. If the app uses `-exec` mode today, blue/green requires moving to a standalone Litestream service.
- Both colours should open the DB with identical pragmas (`journal_mode=WAL`, `busy_timeout=5000`, `wal_autocheckpoint=0` per Litestream guidance). Long read transactions in a draining process can starve checkpoints, which argues for a bounded drain.

### Gaps
- No primary Litestream 0.5 docs were fetched confirming lease semantics for *local* concurrent replicators on the same DB file (the lease is about the object-store destination). Exact lease duration and takeover rules are unconfirmed.
- No engineering blog found that documents a SQLite-specific blue/green write fence in production. The fence design above is inference.

## Background jobs and singleton loops during overlap: avoiding double execution (leader leases, advisory locks)

### Takeaway
The standard pattern is a lease row in the shared database: owner id, `expires_at`, and a heartbeat. The holder renews it, others check it before acting, a lost renewal means abort, and expiry is measured in database time. On top of that, jobs must be idempotent, because leases give at-most-one-leader-at-a-time only modulo clock and pause effects, and delivery is effectively at-least-once. For blue/green, add an explicit handoff: the new process doesn't start singleton loops until it is promoted, and the old one stops them when told to drain.

### Cited Findings
- Singleton leader row with instance id, lease expiry timestamp (followers check before taking over) and last-heartbeat. Only the leader runs the coordinator tick loop — [chronon-core SchedulerLeader (docs.rs)](https://docs.rs/chronon-core/latest/chronon_core/models/struct.SchedulerLeader.html)
- Postgres queue worker: single-row leader table with `expires_at`, renewed on each heartbeat, with expired rows deleted so another worker can claim. Database time is used to avoid clock skew — [Matrix Authentication Service worker.rs](https://element-hq.github.io/matrix-authentication-service/rustdoc/src/mas_storage_pg/queue/worker.rs.html)
- Run-once periodic pattern: each tick tries to acquire the singleton lease, the leader runs the task, and non-leaders skip silently — [udb native_runtime.rs](https://docs.rs/crate/udb/latest/source/src/runtime/service/native_runtime.rs)
- SQLite job store: claims happen inside a transaction relying on SQLite's single-writer lock. The heartbeat extends the lease, and a false heartbeat means the lease was lost, so abort. Delivery is at-least-once, so handlers must be idempotent — [@rootware/jobs DurableJobStore (jsr)](https://jsr.io/@rootware/jobs/doc/~/DurableJobStore)
- Time-based leases can be undermined by clock skew and delayed messages (Litestream maintainer comment) — [Litestream discussion #471](https://git.tdem.in/benbjohnson/litestream/discussions/471)

### Inferences
- Skiff concretely: a `leases(name PRIMARY KEY, holder, generation, expires_at)` table. Acquire or renew with `BEGIN IMMEDIATE; UPDATE ... WHERE name=? AND (holder=? OR expires_at < unixepoch())`, with TTL around 15–30 s and renewal every TTL/3. SQLite's single-writer lock makes the compare-and-set atomic across both processes. Include a monotonically increasing `generation` (fencing token) in side effects where possible.
- Deterministic handoff beats waiting for expiry. Old blue gets "drain" (SIGTERM or a control endpoint), stops loops and *deletes* its lease row, then green acquires on its next tick. If blue crashes, expiry covers it.
- Green should not run singletons during its pre-promotion bake. Gate loop start on "I am the promoted colour", e.g. a row in SQLite written by the orchestrator, or simply the lease. Otherwise a green that later fails health checks may already have run migrations or jobs.
- OS-level alternatives on one host: `flock(2)` on a lock file is released automatically on process death. This is simpler than a DB lease, but invisible to the dashboard. Neither was sourced in this research.

### Gaps
- No primary-source engineering blog found specifically describing scheduler handoff during blue/green overlap. Design guidance above is inferred from general lease patterns.
- `flock` and SQLite-as-advisory-lock semantics were not fetched from man pages.

## How do blue/green systems decide "healthy"? Readiness vs liveness, synthetic checks, error-rate/SLO gates, bake time, automatic rollback triggers

### Takeaway
"Healthy" is layered. Startup and readiness probes gate whether traffic may be sent. Liveness detects a stuck process. Post-cutover analysis (error rate, latency, synthetic checks over a bake window) decides whether to keep the new version or abort back to the still-running old one. The key design choice in Argo Rollouts and Render is keeping the old version up for a delay after the switch, so that rollback is a routing change, not a redeploy.

### Cited Findings
- Kubernetes: startup probes gate the other probes until the app has started, and failure kills the container. Liveness failure means restart. Readiness failure removes the pod from Service endpoints without restarting it, and readiness "run[s] on the container during its whole lifecycle" — [Kubernetes probes docs](https://kubernetes.io/docs/concepts/configuration/liveness-readiness-startup-probes/)
- Argo Rollouts blue/green: `activeService` (production) and `previewService` (test the new version before it serves production). `autoPromotionEnabled` (default true), `autoPromotionSeconds`. `prePromotionAnalysis` must succeed before the switch, and failure aborts with traffic left on the old version. `postPromotionAnalysis` runs after the switch, and failure aborts and switches traffic back to the previous stable ReplicaSet. `scaleDownDelaySeconds` (default 30) keeps the old ReplicaSet after switching — [Argo Rollouts blue/green](https://argo-rollouts.readthedocs.io/en/stable/features/bluegreen/)
- Flagger: metric checks such as `request-success-rate` (percentage of non-5xx, commonly min 99) and latency, run every `interval`. `threshold` is the max number of failed checks before rollback, and on failure the primary keeps 100% of traffic. Blue/green is modelled as iterations with no weight shift. Custom Prometheus/Datadog/etc. metric templates are supported — [Flagger README fork](https://github.com/christian-posta/flagger); [OneUptime Flagger guide (secondary)](https://oneuptime.com/blog/post/2026-03-06-configure-flagger-canary-promotion-thresholds-flux/view)
- AWS CodeDeploy: automatic rollback "when a deployment fails or when a monitoring threshold you specify is met" (CloudWatch alarms). Rollback is a *new* deployment of the last known good revision, not a restore. Scripts' side effects are not reverted — [AWS CodeDeploy rollback docs](https://docs.aws.amazon.com/codedeploy/latest/userguide/deployments-rollback-and-redeploy.html)
- Fly.io: the `bluegreen` strategy boots a new Machine alongside each running one and migrates traffic "only once all the new Machines pass health checks". `canary` boots one, verifies health, then rolls. Smoke checks for about 10 s after start fail the deploy if the Machine keeps crashing — [Fly deploy docs](https://docs.fly.io/launch/deploy). Bluegreen requires HTTP/TCP health checks — [Fly community](https://community.fly.io/t/bluegreen-deploy-strategy-for-a-non-tcp-http-service/19213). One user reported green machines passing checks "immediately" before they had really booted, which shows the risk of a shallow health endpoint — [Fly community](https://community.fly.io/t/blue-green-deployment-always-deploy-instantly/27642). Volume support with bluegreen is reported as problematic but is unconfirmed officially — [third-party](https://alchemy.run/fly/compute/deployments/)
- Render: keeps the original instance for 60 s after the new one receives traffic, then SIGTERM, then SIGKILL after 30 s (up to 300 s). If any new instance fails to become healthy, the entire deploy is cancelled and reverts to the previous version. Failed build or pre-deploy steps leave the old version running — [Render deploys](https://render.com/docs/deploys)
- kamal-proxy and Dokku use a single HTTP check (default `/up` at 1 s for kamal; configurable attempts, wait and timeout for Dokku) as the only gate, with no post-cutover analysis — [kamal-proxy source](https://github.com/basecamp/kamal-proxy/blob/main/internal/server/service.go); [Dokku](https://dokku.com/docs/deployment/zero-downtime-deploys/)

### Inferences
- A layered gate for Skiff. (1) Process up and sd_notify `READY=1`. (2) Readiness endpoint on the green socket checks DB open, migrations applied, schema version matches the binary, and critical subsystems initialised. It must not just return 200, given the Fly "passes immediately" pitfall. (3) Synthetic smoke requests from the orchestrator straight to the green socket: log in or render the dashboard, plus a read-only API call. (4) Cutover via Caddy PATCH. (5) Bake window (e.g. 60–120 s, like Render's 60 s and Argo's 30 s default) while blue stays up but idle. Watch green's 5xx rate (Caddy access logs or app metrics), liveness, and crash or restart count. (6) If the bake fails, PATCH back to blue, which is instant because blue is still running, then stop green. (7) If it passes, stop blue and keep its release directory for a cold rollback.
- Automatic rollback triggers worth implementing: green exits or systemd restarts it during the bake, readiness flaps, the 5xx ratio passes a threshold over N requests, or the orchestrator's own heartbeat to the new control plane fails. Prefer Render-style "cancel everything and revert" semantics.
- The orchestrator must live outside the control plane being replaced, e.g. a small oneshot unit or the privileged helper. Otherwise the thing deciding to roll back is the thing being swapped.

### Gaps
- Official Flagger docs (docs.flagger.app) were not fetched directly. Flagger details come from README forks and secondary guides.
- Fly.io `wait_timeout` and official bluegreen and volume constraints were not confirmed from official docs.
