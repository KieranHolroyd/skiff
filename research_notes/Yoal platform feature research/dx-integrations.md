# Developer Experience and Integration Features Across Deployment Platforms (November 2026)

Scope: the workflow/integration layer — Git providers, CLI, API/SDK/IaC, webhooks/notifications, preview collaboration, templates and local development. Runtime internals are out of scope. Yoal baseline is taken from this repository (`apps/cli/README.md`, `docs/API.md`, `docs/DESIGN.md`, `docs/ROADMAP.md`).

Method note: the web search integration returned no results throughout this session, so findings come from directly fetching primary documentation pages (official docs, GitHub docs, provider repositories). Where a page could not be fetched, that is recorded under Gaps rather than guessed.

## Git workflows (app installs, repo/branch selection, monorepos, ignored builds, PR previews, checks, merge queues, caching, logs, secret sync)

### Takeaway
The table stakes in 2026 are no longer "connect a repo and build on push". Mature platforms ship a GitHub App with granular permissions, a sticky PR comment with the preview URL, commit statuses/checks that can be required for merge, monorepo watch paths so unrelated pushes do not build, and merge-queue awareness. Yoal currently has repo-level webhooks and build records but none of the collaboration signal (comments, checks, deployment statuses) that makes PR previews usable by a team.

### Cited Findings
- Cloudflare Workers Builds connects repositories hosted on GitHub, GitLab or Cloudflare Artifacts; build settings include git account, repository, production branch, build command, deploy command, preview command, root directory for monorepos, an API token, and build-only variables/secrets — [Cloudflare Workers Builds configuration](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/).
- Cloudflare runs a two-step build (optional build command, then deploy command); preview builds run a separate preview command for any branch that is not the production branch and produce a Preview URL; build logs are retained for 90 days — [Cloudflare Workers Builds](https://developers.cloudflare.com/workers/ci-cd/builds/), [configuration](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/).
- Cloudflare's autoconfig detects a framework when no Wrangler config exists, opens a pull request with the generated configuration, produces a preview deployment, and configures the project after merge — [Cloudflare Workers Builds](https://developers.cloudflare.com/workers/ci-cd/builds/).
- Cloudflare says supported external providers can post the Preview URL as a pull request comment; it does not claim to post the comment itself for every provider — [Cloudflare Workers Builds](https://developers.cloudflare.com/workers/ci-cd/builds/).
- Netlify builds Deploy Previews automatically for pull/merge requests from GitHub, GitLab, Bitbucket, Azure DevOps and Cursor Origin; preview URLs follow `deploy-preview-<number>--<site>` and remain stable as commits are pushed — [Netlify Deploy Previews](https://docs.netlify.com/deploy/deploy-types/deploy-previews/).
- Netlify adds a status to the pull/merge request as the preview builds, and (when deploy notifications are enabled) adds a PR comment with the preview link once ready — [Netlify Deploy Previews](https://docs.netlify.com/deploy/deploy-types/deploy-previews/).
- Netlify GitHub-connected sites get GitHub commit statuses, PR comments and commit checks by default; the PR comment updates in place as commits are added, and the check carries richer deploy detail — [Netlify deploy notifications](https://docs.netlify.com/deploy/deploy-notifications/).
- Netlify supports GitLab commit statuses/MR comments, Bitbucket commit statuses/PR comments, and Azure DevOps commit statuses/PR comments, several requiring a personal access token with `api` scope — [Netlify deploy notifications](https://docs.netlify.com/deploy/deploy-notifications/).
- Netlify CLI v16+ executes from the monorepo workspace root (the highest-level `package.json`), auto-detects monorepos, and exposes `--filter <package-or-path>` so commands can run from the repo root — [Netlify CLI](https://docs.netlify.com/api-and-cli-guides/cli-guides/get-started-with-cli/).
- When PR environments are enabled, Railway creates a temporary environment when a PR opens and deletes it when the PR merges or closes; "Focused PR Environments" deploy only services affected by changed files, using watch paths or root directory plus dependency references, and the GitHub PR comment lists which services were skipped — [Railway environments](https://docs.railway.com/guides/environments).
- Railway can create PR environments for bot-authored PRs (Dependabot, Renovate, GitHub Copilot, Claude Code, Devin, Jules and others) via an "Enable Bot PR Environments" toggle — [Railway environments](https://docs.railway.com/guides/environments).
- GitHub deployment statuses support `error`, `failure`, `inactive`, `in_progress`, `pending`, `queued`, `success`, plus `environment`, `environment_url`, `log_url` and a 140-character `description`; prior statuses are retained 90 days — [GitHub REST deployment statuses](https://docs.github.com/en/rest/deployments/statuses).
- Creating a deployment status with `auto_inactive: true` (the default) marks prior successful deployments in the same non-production environment inactive — [GitHub REST deployment statuses](https://docs.github.com/en/rest/deployments/statuses).
- GitHub merge queues require required checks to be reported on the `merge_group` event; third-party CI must run on branches prefixed `gh-readonly-queue/{base_branch}`, which carry a different SHA from the PR — [GitHub merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue).
- GitHub Apps get no permissions by default, request repository/organization/account permissions explicitly, see only webhook events their permissions allow, and installation access tokens are scoped to the installation's selected repositories — [GitHub App permissions](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app).
- Yoal's current git surface is `GET|PUT|DELETE /projects/:slug/git` (source, branch, build/output dirs, webhook secret) and `GET|POST /projects/:slug/builds`, with build status and full log per build — [Yoal API docs](https://github.com/KieranHolroyd/yoal/blob/main/docs/API.md).
- Yoal's roadmap lists "Git builds on the homelab Builder + GitHub webhooks" as a v2 item, and the dashboard already has build surfaces — [Yoal roadmap](https://github.com/KieranHolroyd/yoal/blob/main/docs/ROADMAP.md).

### Inferences
- **Bundle 1 — GitHub App, PR comment, checks, deployment status (medium, highest Git priority).** Problem: today a solo developer must create a webhook secret per repo, and reviewers get no signal in the PR. A single GitHub App with `contents:read`, `checks:write`, `pull_requests:write`, `deployments:write` and `metadata:read` gives an install flow with repo selection, replaces per-repo secrets, and enables a sticky comment ("Preview ready — url, commit, build log") plus a check run and a deployment record with `environment_url`/`log_url`. This is the difference between "CI that deploys" and "a platform a team can review on".
- **Sticky comment, not a new comment per push (small).** Problem: notification spam. Netlify explicitly updates the same PR comment; Yoal should store the comment id per (project, PR) and PATCH it.
- **Monorepo root + watch paths + ignored builds (medium).** Problem: every push builds every project and burns the homelab builder; a docs-only change redeploys production. Adopt Cloudflare's `root directory` and Railway's `watch paths`, plus a `yoal.json` `build.watch` glob list and an `ignore` list. Detect the app root from lockfile/package.json when unset. Store "skipped, no matching changes" as a first-class build result so the PR comment can say so.
- **Merge queue correctness (small).** Problem: if Yoal reports a required check only on `pull_request`, enabling GitHub's merge queue silently blocks merges. Handle `merge_group`/`gh-readonly-queue/*` by building the merge-group SHA and reporting a check, or explicitly document that Yoal checks must not be required. Also ensure a merge-queue push does not deploy production twice (dedupe by tree/SHA).
- **Deploy-on-merge and production branch setting (small).** Problem: preview and production behaviour are implicit. Add an explicit `productionBranch` and `autoPromote` per project; only the production branch moves the pointer, everything else is a preview.
- **Build log streaming + retention (small–medium).** Problem: agents and developers cannot watch a build; they poll. Yoal already stores ordered log events with a cursor, so add SSE/`--follow` on the API and CLI, and a retention policy (Cloudflare keeps 90 days).
- **Build caching (medium–large).** Problem: slow, expensive repeated dependency installs on a homelab builder. Cache package-manager stores keyed by lockfile hash, exposed as a per-build "cache hit" line. Vercel exposes a remote artifact cache API (`/v8/artifacts/*`) as a product; Yoal can start with a local builder cache only.
- **Build-time secret sync (medium).** Problem: secrets configured for runtime are not available to the build, and per-environment values drift. Separate `build` vs `runtime` scopes (Cloudflare does this), and add `yoal env pull` so local builds use the same values.
- **GitLab first, Bitbucket later (large each).** Problem: self-hosted teams often run GitLab. Netlify's manual path (deploy key + webhook, PAT for MR comments) is a cheap interim; a GitLab OAuth app with MR notes/commit statuses is the real integration. Bitbucket is lower priority for a solo/small-team ICP.
- **Do not copy Railway's "bot PR environments" toggle yet.** It is a differentiator for agent-heavy teams, but Yoal's previews already key off branches; the missing piece is commenting/checking, not environment creation.

### Gaps
- No primary source found quantifying how much PR comments/checks improve review latency or adoption; the argument here is qualitative.
- Cloudflare's docs describe preview URL commenting only vaguely ("supported external providers"), so it is unclear whether Cloudflare posts a native PR comment for GitHub/GitLab today.
- No public documentation found on Yoal's exact git-build implementation state (the roadmap box is unchecked while the API is documented), so effort estimates assume the API surface is real but the GitHub App/checks layer is absent.
- Build-cache semantics for Cloudflare Workers Builds were not documented on the pages fetched; do not claim parity there.

## CLI (login, link, dev, deploy, env pull, logs tail, open, rollback, promote, domains, whoami, machine-readable output, completions, offline, CI tokens, stdin/directory, config file)

### Takeaway
The 2026 CLI is a project-aware, agent-aware client, not a bag of deploy commands. The strongest patterns are: link a directory once and stop passing `--project`; pull remote env into local files; tail logs and wait on deploys with meaningful exit codes; emit stable JSON in non-TTY/CI; and have the CLI itself install MCP/skills/AGENTS.md for coding agents. Yoal already has browser PKCE login, profiles, `--json`, deploy/status/logs/open/promote/rollback — the gaps are link, dev, env, tail, whoami/doctor, completions and agent setup.

### Cited Findings
- Vercel CLI has dedicated commands for `link`, `dev`, `env` (including `env pull` and `env run`), `logs`, `open`, `rollback`, `promote`, `whoami`, `domains`, `deploy`, `pull`, `redeploy`, `inspect`, `api`, `curl`, `comments`, `deploy-hooks`, `webhooks`, `tokens`, `target` (custom environments), `init`, `mcp`, `setup`, `agent init`, `skills`, `doctor`, `bisect` and `ci`; `vercel ci` is labelled Beta — [Vercel CLI](https://vercel.com/docs/cli) (page last updated 2026-10-07).
- Vercel CLI explicitly supports CI auth via `VERCEL_TOKEN` or `--token`, preferring the environment variable because command-line tokens are visible in process lists/logs — [Vercel CLI](https://vercel.com/docs/cli).
- Vercel CLI's `comments` command can list threads, inspect a thread and resolve it with a message; `curl` makes requests with automatic deployment-protection bypass; `api` makes authenticated HTTP requests to the Vercel API from the terminal — [Vercel CLI](https://vercel.com/docs/cli).
- Vercel's `agent init` generates an `AGENTS.md` with deployment best practices; `setup` configures coding agents (Vercel plugin for Claude Code and Codex, AI Gateway); `skills` discovers agent skills; `mcp` writes MCP client configuration — [Vercel CLI](https://vercel.com/docs/cli).
- Railway CLI has `login --browserless`, `link`, `unlink`, `status`, `open`, `up --detach`, `redeploy`, `down`, `logs --build/-n`, `run`, `shell`, `dev`, `variable`, `environment`, `domain`, `completion`, `whoami`, `mcp install`, `skills install`, `setup agent`, and `api` (GraphQL query/schema/describe) — [Railway CLI](https://docs.railway.com/guides/cli).
- Railway's recommended install is `curl -fsSL agents.railway.com | sh`, which installs the CLI and runs `railway setup agent` to configure detected agent tools — [Railway CLI](https://docs.railway.com/guides/cli).
- Railway separates `RAILWAY_TOKEN` (project-level) from `RAILWAY_API_TOKEN` (account/workspace-level) for CI — [Railway CLI](https://docs.railway.com/guides/cli).
- Vercel MCP is a remote OAuth server at `https://mcp.vercel.com`, installable with `npx add-mcp https://mcp.vercel.com`, and documents setup for Claude Code, Claude.ai/Desktop, ChatGPT, Codex CLI, Cursor, VS Code, Devin, Raycast, Goose, Windsurf, Gemini, OpenCode and Pi; it supports CIMD client identification — [Vercel MCP](https://vercel.com/docs/agent-resources/vercel-mcp) (2026-09-15).
- Netlify offers a remote MCP at `https://netlify-mcp.netlify.app/mcp` and a local MCP via `npx @netlify/mcp`, plus installable agent skills (`npx skills add netlify/context-and-tools --skill '*' --yes`) covering functions, blobs, config, CLI/deploy and frameworks — [Netlify agent setup](https://docs.netlify.com/build/build-with-ai/netlify-mcp-server/).
- Render CLI supports `-o json|yaml|text`, `RENDER_OUTPUT`, `--confirm`, and auto-selects `text` in non-TTY environments; `deploys create --wait` exits non-zero on a failed deploy and accepts `--commit <sha>` — [Render CLI](https://render.com/docs/cli).
- Render CLI exposes `blueprints validate` for `render.yaml`, `psql`/`ssh` sessions, and `skills install` for Claude Code, Codex, OpenCode and Cursor — [Render CLI](https://render.com/docs/cli).
- Netlify CLI supports `netlify clone owner/repo` to clone and link in one command, `netlify link` to write `siteId` into `.netlify/state.json`, `netlify build --dry`, `env:set`/`env:list`/`env:get`/`env:import`/`env:clone`, `--filter` for monorepos, and `netlify create "<prompt>"` to generate, deploy and download a project — [Netlify CLI](https://docs.netlify.com/api-and-cli-guides/cli-guides/get-started-with-cli/).
- Netlify CLI recommends installing locally and pinning a version in CI, rather than a global install, for reproducible builds — [Netlify CLI](https://docs.netlify.com/api-and-cli-guides/cli-guides/get-started-with-cli/).
- Yoal CLI currently ships `login`, `logout`, `config`, `profile`, `deploy [dir]`, `status`, `projects`, `deployments`, `promote`, `rollback`, `logs`, `open`; most accept `--json`, and browser login uses a loopback redirect with PKCE — [Yoal CLI README](https://github.com/KieranHolroyd/yoal/blob/main/apps/cli/README.md).
- Yoal CLI already supports multiple profiles (`yoal profile use`, `YOAL_PROFILE`) and per-profile config at `~/.config/yoal/config.json` with `0600` permissions — [Yoal CLI README](https://github.com/KieranHolroyd/yoal/blob/main/apps/cli/README.md).

### Inferences
- **`yoal link` (small, highest CLI priority).** Problem: every command needs `--project`, and CI needs a hard-coded slug. Write `.yoal/project.json` (project id/slug, org, content domain, default environment) on first deploy or explicit link, walk up parent directories, and let `deploy/status/logs/open` resolve it. Precedence: flag > env (`YOAL_PROJECT`) > linked file > prompt. Netlify's `.netlify/state.json` is the proven shape.
- **`yoal env pull` / `env push` / `env run` (small–medium).** Problem: local builds and agent test runs drift from the deployed environment; secrets are copied by hand. `env pull` writes `.env.local` (framework-aware: `.env`, `.env.local`, `.dev.vars`), with `--environment` and `--project`; values are only returned for permitted scopes. `env run -- <cmd>` injects them without writing a file. This pairs with a build/runtime secret split.
- **`yoal logs -f` / `--build` (small).** Problem: users poll `yoal logs` and cannot see a live build. The API already returns a cursor; add follow mode with backoff and `--json` newline-delimited events. Also add `yoal deployments <project> --follow` or `yoal deploy --wait` that exits non-zero on failure, like Render's `--wait`.
- **`yoal whoami` + `yoal doctor` (small).** Problem: auth/profile/network failures are opaque, especially for agents. `whoami --json` returns user, org, role, effective scopes, platform URL, token expiry. `doctor` checks binary version, config permissions, DNS/TLS, API reachability, MCP endpoint and content-domain resolution, and prints one fix per problem (Vercel's doctor).
- **Shell completions (small).** Problem: discoverability and speed. `yoal completion bash|zsh|fish` plus generated man pages; Railway ships this and it is cheap.
- **`yoal deploy` from stdin/tarball and `--prebuilt` (small).** Problem: agents and CI often have an archive, not a directory; piping avoids temp dirs. Support `yoal deploy -` (tar/zip on stdin), `--prebuilt` to skip framework detection, and `--no-build` for artifact-only deploys. Keep the directory form as the default.
- **Stable machine contract (small).** Problem: `--json` shapes drift and scripts break. Version the envelope (`{"ok":true,"data":…,"meta":…}` / `{"ok":false,"error":{code,message,suggestions}}`), document exit codes (0 success, 1 user error, 2 usage, 3 auth, 4 conflict, 5 server), auto-JSON when `!isTTY` or `CI=true` (Render), honour `NO_COLOR`, and add `--quiet`. Publish the schema with the OpenAPI work.
- **Agent bootstrap (small, outsized leverage).** Problem: Yoal already runs a remote OAuth MCP server, but connecting Claude Code/Codex/OpenCode is manual JSON editing, and agents do not know Yoal's conventions. Add `yoal setup agent` (detect Claude Code, Codex, OpenCode, Cursor; write MCP config; print the OAuth step), `yoal mcp install`, `yoal agent init` (write `AGENTS.md` with deploy/preview/secret rules), and `yoal skills` (serve/install a small Yoal skill). Railway, Vercel, Netlify and Render all ship a version of this in 2026; the differentiator for Yoal is doing it against a self-hosted URL with no central service.
- **CI tokens and OIDC (medium).** Problem: long-lived `yoal_…` keys in CI. Add `yoal token create --project --environment --ttl --name`, show the token once, support revocation by name, and add GitHub Actions OIDC exchange so a workflow can mint a short-lived deploy token without a stored secret. Keep `YOAL_TOKEN` as the fallback.
- **Offline behaviour (medium, lower priority).** Problem: `yoal status` fails on a plane or when the control plane is down. Cache last-known status/deployments in the profile dir, serve it with a `stale: true` marker and timestamp, and queue nothing (deploys must fail loudly). This is a nice-to-have for a solo developer, not table stakes.
- **Domains subcommand (small).** Problem: adding a domain currently means the dashboard or raw REST. `yoal domains add/list/check/rm` mirrors the existing REST endpoints and fits the "everything in the terminal" expectation.
- **Config file (small).** Problem: project-level defaults (framework, output dir, build command, environment) live only in the dashboard. Add `yoal.json` read by CLI and builder, with CLI flags overriding it. This is also the foundation for config-as-code.

### Gaps
- No primary source found on Vercel CLI's shell-completion support; Railway's `completion` command is the cited example.
- "Offline behaviour" is not documented as a feature by any platform surveyed; the recommendation is a design inference, not parity.
- No data on how often developers use `--json` vs human output, so the priority of auto-JSON is judgment-based.
- Yoal's current `logs` cursor semantics were read from `docs/API.md`; the CLI implementation may already follow the cursor internally (not verified line-by-line).

## API / SDK / IaC (REST/GraphQL quality, OpenAPI, typed clients, Terraform/Pulumi, config-as-code, drift, deploy tokens, webhooks/event catalog)

### Takeaway
Two models dominate. Vercel offers a very broad REST API plus a CLI passthrough and a Terraform provider; Railway offers a single introspectable GraphQL schema with explicit deprecation, rate-limit and retry contracts, plus a typed TypeScript IaC DSL with `plan/apply`, redacted plans, drift exit codes and saved plan artifacts. For Yoal, the highest-return sequence is OpenAPI + a typed client first, then `yoal.json` config-as-code with plan/apply, and only then a Terraform provider — a provider is a large maintenance commitment and should ride on a stable spec.

### Cited Findings
- Vercel documents a broad REST API (projects, deployments, env vars, domains, logs, checks, artifacts cache, webhooks/events, integrations) and its CLI exposes `vercel api` for authenticated passthrough requests — [Vercel REST API](https://vercel.com/docs/rest-api) (page last updated 2026-11-04), [Vercel CLI](https://vercel.com/docs/cli).
- Vercel publishes a Terraform provider (MPL-2.0, Go, Terraform 1.11+); its acceptance tests require GitHub, Bitbucket and GitLab repository fixtures, indicating project/deployment support across all three providers — [vercel/terraform-provider-vercel](https://github.com/vercel/terraform-provider-vercel).
- Cloudflare publishes a Terraform provider (Apache-2.0) configured with an API token, account ID and zone ID; the README shows provider version `~> 5.28.0` and says the provider is auto-generated from the Cloudflare API and no longer accepts community PRs — [cloudflare/terraform-provider-cloudflare](https://github.com/cloudflare/terraform-provider-cloudflare).
- Railway's public API is GraphQL at `https://backboard.railway.com/graphql/v2`, supports introspection, and treats the schema as the contract: additive changes need no version bump, retired fields are `@deprecated` with a reason and sunset window — [Railway public API](https://docs.railway.com/integrations/api).
- Railway documents rate-limit headers (`RateLimit-Policy`, `X-RateLimit-*`, `Retry-After`), a 429 contract, GraphQL error codes (`GRAPHQL_VALIDATION_FAILED`, `BAD_USER_INPUT`, `INTERNAL_SERVER_ERROR`) and a `traceId`, plus retry guidance (reads safe, writes only on network/429/5xx without a response) — [Railway public API](https://docs.railway.com/integrations/api).
- Railway issues four token types: account, workspace, project (scoped to one environment) and OAuth; project tokens use a `Project-Access-Token` header rather than `Authorization: Bearer` — [Railway public API](https://docs.railway.com/integrations/api).
- Railway IaC uses `.railway/railway.ts` (generally available), with `.py`/`.go` authoring in beta; commands are `config init`, `config pull`, `config plan`, `config apply` — [Railway Infrastructure as Code](https://docs.railway.com/infrastructure-as-code).
- Railway's `config plan` redacts variable values as `«hidden»` by default, supports `--detailed-exit-code` (0 = no changes, 2 = changes pending) for CI drift gating, and `--json`; `config apply` re-plans immediately before applying and rejects a stale plan — [Railway Infrastructure as Code](https://docs.railway.com/infrastructure-as-code).
- Railway supports saved plan artifacts (`--out`, `--plan`) that fail if the live `configEtag` or checked-out `.railway/` tree drifted; destructive changes require `--confirm-destructive` even with `--yes`; named partials give per-repo ownership in multi-repo projects — [Railway Infrastructure as Code](https://docs.railway.com/infrastructure-as-code).
- Railway's GitHub Action (`railwayapp/config`) posts a plan comment on PRs touching `.railway/`, and applies the reviewed plan on merge; fork PRs are skipped — [Railway Infrastructure as Code](https://docs.railway.com/infrastructure-as-code).
- Netlify publishes a JSON Schema for `netlify.toml` at `https://open-api.netlify.com/netlify.schema.json` and recommends adding `"$schema"` so editors and agents validate configuration — [Netlify agent setup](https://docs.netlify.com/build/build-with-ai/netlify-mcp-server/).
- Yoal's API is a hand-documented REST v1 surface (markdown table) with Bearer API keys, session cookies, CSRF Origin checks, and JSON errors; no OpenAPI document is published — [Yoal API docs](https://github.com/KieranHolroyd/yoal/blob/main/docs/API.md).
- Yoal exposes deploy tokens only as general API keys created via `/api/auth/api-key/create` or the dashboard; secrets are write-only over API/MCP — [Yoal README](https://github.com/KieranHolroyd/yoal/blob/main/README.md), [API docs](https://github.com/KieranHolroyd/yoal/blob/main/docs/API.md).
- Yoal has a generic alert webhook (email, ntfy, Discord, Home Assistant) for ops events, not a deploy-scoped event catalogue — [Yoal design](https://github.com/KieranHolroyd/yoal/blob/main/docs/DESIGN.md).

### Inferences
- **Publish OpenAPI 3.1 generated from the existing Zod contracts (small–medium, highest API priority).** Problem: agents and humans guess request/response shapes from a markdown table; every SDK and Terraform provider becomes hand-written. Add `GET /api/openapi.json` (and `/api/v1/openapi.json`), a Redoc/Scalar page, `$schema`-style examples, error schemas, and a CI check that the spec matches the routes. This is the single highest-leverage API investment because it unlocks typed clients, agent tooling and IaC.
- **Typed client package (medium).** Problem: every integration re-implements auth, retries and pagination. Ship `@yoal/sdk` (TypeScript, generated from OpenAPI) with `deploy`, `promote`, `rollback`, `logs`, `env`, `domains`; include a `yoal/client` subpath for browser-safe reads. Python can follow if demand exists. Keep the CLI built on the SDK so the SDK is dogfooded.
- **`yoal.json` config-as-code + `yoal config plan/apply` (medium).** Problem: project settings, env names, domains and build config live only in the dashboard, so environments cannot be reviewed or reproduced. Adopt a schema-first file (`$schema`, framework, root, build/output, watch/ignore, environments, domains, access, secret *references* not values), then `plan` (redacted diff, drift exit code 2, `--json`) and `apply` (re-plan before apply, reject stale, destructive confirmation). This directly mirrors Railway's model and is a better fit for a self-hosted solo/small team than Terraform.
- **Terraform provider (large, defer).** Problem: teams with existing Terraform want Yoal in the same graph. But a provider is a permanent compatibility surface (Vercel's is a full Go repo with acceptance tests; Cloudflare's is auto-generated and still has 200+ issues). Do it only after OpenAPI + config-as-code are stable; start with resources for project, environment, domain, secret metadata and deploy token. A community provider is acceptable as a stopgap, but do not promise drift detection until `plan` is trustworthy.
- **Pulumi (large, skip).** No primary evidence gathered that Pulumi providers are a deciding factor for this ICP; the Terraform-compatible route plus a typed TS SDK covers most of the same users. Revisit only on demand.
- **Scoped deploy tokens (small–medium).** Problem: today a CI token is a full user API key; leaking it exposes every project. Add tokens bound to `(project, environment, permissions, expiry)`, display once, list/revoke by name, and include the scope in `whoami`. Railway's project token is the model. Pair with GitHub OIDC for short-lived minting.
- **Event catalogue + signed webhooks (medium).** Problem: the only outbound hook is an ops alert; teams cannot wire "deploy failed" into Slack, a changelog, or an agent. Define events (`deploy.queued|started|succeeded|failed|promoted|rolled_back`, `build.*`, `domain.verified|drift`, `secret.created|deleted`, `member.*`), sign with HMAC (`X-Yoal-Signature`, timestamp, delivery id), retry with exponential backoff, expose a delivery log with replay, and document payload schemas. Netlify's deploy event list (including locked/unlocked, request pending/accepted/rejected, restored) is a good completeness checklist.
- **SSE/event stream for agents (small–medium).** Problem: agents poll `GET /deployments` and `GET /logs`. Add `GET /api/v1/events?after=<cursor>` (SSE) with the same event catalogue; the CLI's `--follow` and MCP tools can share it.
- **Idempotency and concurrency (small).** Problem: retried deploy/promote requests create duplicates or race. Accept `Idempotency-Key` on POST deploy/promote/share/token, store the result for 24h, and return `409` with the existing resource on conflict.
- **API hygiene (small).** Problem: agents cannot tell whether to retry. Add `X-Request-Id`/`traceId` to every response, stable machine error codes (`conflict`, `rate_limited`, `insufficient_scope`), `Retry-After` on 429, and rate-limit headers. Railway's contract is the best written example.
- **Do not add GraphQL.** Problem: it doubles the surface for a small team and Yoal's REST + OpenAPI is sufficient. Railway's GraphQL is a consequence of its dashboard architecture; Yoal's SvelteKit app already speaks REST. Invest in OpenAPI instead.

### Gaps
- The Terraform Registry pages for Vercel and Cloudflare did not render (JavaScript app, empty fetch); provider facts come from their GitHub repositories instead.
- No OpenAPI document URL was confirmed for Vercel in the fetched pages; the claim is limited to "broad documented REST API", not "published OpenAPI".
- Pulumi provider coverage for Vercel/Cloudflare/Railway was not verified; the "skip" recommendation is a judgment call, not a sourced market fact.
- No public data on Yoal's API error/rate-limit behaviour beyond the docs table; token scoping details were inferred from the RBAC description.

## Collaboration (preview comments/annotations, screenshot diffs, shareable links, access control, review approvals, notifications, changelog/release notes)

### Takeaway
Preview collaboration has split into two layers: lightweight, high-adoption signals (sticky PR comment, preview URL, password/protection, Slack notification) and heavyweight in-page review (toolbar comments, annotations, screenshot/video capture). Yoal should ship the first layer now; the second is a large product bet that only makes sense after preview traffic and team usage exist. Vercel and Netlify both treat "who can see/comment on this preview" as a first-class access-control problem.

### Cited Findings
- Vercel Comments are enabled by default on all preview deployments, on all plans, free; they require the Vercel Toolbar and a Vercel account, support threads on any part of the UI, link to Slack threads, and email the PR owner/participants — [Vercel Comments](https://vercel.com/docs/comments) (2026-08-19).
- Vercel lets a preview be shared with individual external collaborators (Pro/Enterprise), with "anyone" or "anyone with the link" comment permissions, and supports access requests that the owner approves or denies; shareable links can bypass deployment protection — [Vercel sharing deployments](https://vercel.com/docs/deployments/sharing-deployments) (2026-08-28).
- Vercel distinguishes branch links (always latest commit) from commit links (frozen to a commit) when sharing — [Vercel sharing deployments](https://vercel.com/docs/deployments/sharing-deployments).
- Netlify's Deploy Preview collaboration happens in the Netlify Drawer: comments, screenshots and video, responsive testing, opened with `⌘\`/`^\`; previews can be password-protected and receive `X-Robots-Tag: noindex` — [Netlify Deploy Previews](https://docs.netlify.com/deploy/deploy-types/deploy-previews/).
- Netlify lets a PR description set the preview entry path with `@netlify /path`, which updates the link in the PR comment — [Netlify Deploy Previews](https://docs.netlify.com/deploy/deploy-types/deploy-previews/).
- Railway's PR comment lists services skipped by focused PR environments, making partial previews explicit — [Railway environments](https://docs.railway.com/guides/environments).
- Netlify deploy notifications cover started, succeeded, failed, deleted, locked, unlocked, request pending/accepted/rejected, restored, and previously-failed/succeeded transitions; channels include Slack, email (Pro/Enterprise), HTTP webhook with a JWS `X-Webhook-Signature`, and Git-provider statuses/comments/checks — [Netlify deploy notifications](https://docs.netlify.com/deploy/deploy-notifications/).
- Vercel's CLI can manage Toolbar comment threads (`list`, `inspect`, `resolve -m`), which shows comments are API-addressable, not just UI state — [Vercel CLI](https://vercel.com/docs/cli).
- Yoal already has share links with expiry, caps, emails and revocation, plus `public`/`password`/`platform` access modes for production and previews — [Yoal API docs](https://github.com/KieranHolroyd/yoal/blob/main/docs/API.md), [roadmap](https://github.com/KieranHolroyd/yoal/blob/main/docs/ROADMAP.md).
- Yoal has no deployment comments, review approvals or in-page annotation surface; the roadmap lists none — [Yoal roadmap](https://github.com/KieranHolroyd/yoal/blob/main/docs/ROADMAP.md).

### Inferences
- **Sticky preview comment + "Preview" section in the dashboard (small, do first).** Problem: reviewers cannot find the preview or tell whether it is current. Include URL, commit, build status, expiry, access mode, and a "stale — newer commit available" marker. Update in place. This is 80% of the value of a toolbar at 10% of the cost.
- **Per-deployment share links with access modes (small–medium).** Problem: Yoal share links are project-scoped; reviewers need a link to *this* preview, optionally expiring and password-protected. Add `share` on a deployment with `expiresAt`, `maxViews`, `password`, `emails`, `allowComments`; show "anyone with link" vs "platform users" in the UI. Yoal's existing share infrastructure is most of the work.
- **Access requests (medium).** Problem: a stakeholder hits a protected preview and has to ask an admin out-of-band. Add "request access" on the 401/403 page, email the owner, and an approve/deny list per deployment (Vercel model). Requires email + a small approval table.
- **Review approvals as a promote gate (medium).** Problem: a small team wants "one approval before production" without a full RBAC product. Record `approved_by`/`approved_at` per deployment; `promote` can require N approvals for a project; the CLI/MCP returns `409 approval_required`. This is cheaper and more useful than comment-level approvals.
- **In-page comments/annotations (large, defer).** Problem: design review needs element-level feedback. But this requires a toolbar script injected into previews, auth handoff, anchoring across DOM changes, screenshot storage and notification fan-out. Netlify's Drawer and Vercel's Toolbar are mature; a self-hosted solo team likely prefers a PR comment + Slack. Revisit after the lightweight layer ships; consider embedding an existing open-source annotation tool rather than building.
- **Screenshot diffs (large, skip).** Problem: visual regressions. This is a testing product (baseline storage, diff algorithm, approval UI, CI integration) and is better served by Playwright/Chromatic-style tools. If needed, expose a per-deployment screenshot URL and let external CI compare.
- **Deploy notifications via Slack/Discord/email (medium).** Problem: the team lives in chat; the dashboard is not checked. Extend the existing `Notifier` from ops alerts to deploy/build events, with per-project routing, a compact message (project, env, status, commit, preview link, actor) and a "mute previews" option. Discord is a webhook POST; Slack needs a bot/app for threading. Email should be per-user opt-in, not per-project.
- **Release notes / changelog (small–medium).** Problem: after a promote, nobody can say what changed. Generate a changelog from commits between the previous and new production deployment (conventional commits or PR titles), store it on the deployment, show it in the promote confirmation and `yoal promote --notes`, and expose `GET /deployments/:id/changelog`. This is cheap because Yoal already has git metadata for builds; it becomes a differentiator for agent-driven deploys ("what did the agent ship?").
- **Preview noindex + banner (small).** Problem: previews get indexed or mistaken for production. Add `X-Robots-Tag: noindex` to preview responses and an optional small "Preview — <commit>" banner injected at the edge (or documented as a `_headers` recipe). Netlify does the header by default.
- **Do not build a full notification preference centre yet.** Start with project-level channel config and a global mute; per-event subscriptions can follow once the event catalogue exists.

### Gaps
- No usage or conversion data was found for preview comments/toolbars; the "defer" recommendation is based on implementation cost, not measured demand.
- Vercel's comments pricing/plan details were clear, but no source quantifies comment volume or review outcomes.
- No primary source on how Yoal's share-link caps/emails behave at the edge (the API docs describe creation; agent enforcement was not read in depth).
- Screenshot-diff tooling was not surveyed; "skip" reflects scope, not a claim that the market lacks demand.

## Templates and scaffolding (starter templates, one-click examples, framework detection, `create` commands, agent-friendly scaffolding)

### Takeaway
Templates are becoming an agent on-ramp, not a gallery. Cloudflare's `create-cloudflare` offers templates, arbitrary git sources (subdirectory/branch/commit), and an explicit "add an AGENTS.md" prompt; Netlify's `netlify create "<prompt>"` generates, deploys and downloads a project; Vercel's `vercel init` pulls examples; Railway has template search and `railway deploy --template`. Yoal's template story is explicitly "later", which is a missed cheap win for an agent-first platform.

### Cited Findings
- Cloudflare's C3 (`npm create cloudflare@latest`) scaffolds a Worker, offers templates, asks whether to add an `AGENTS.md` for AI coding tools, and can create from an existing git source including `user/repo`, subdirectories, branches and commit hashes, plus Bitbucket/GitLab prefixes — [Cloudflare Workers CLI guide](https://developers.cloudflare.com/workers/get-started/guide/) (2026-10-12).
- Cloudflare C3 can initialize git and optionally deploy the new project as part of the flow — [Cloudflare Workers CLI guide](https://developers.cloudflare.com/workers/get-started/guide/).
- Netlify's `netlify create "<natural-language prompt>"` generates a project via Agent Runners, deploys it to a live URL, downloads the code locally, and can create/connect a GitHub repo for continuous deployment — [Netlify CLI](https://docs.netlify.com/api-and-cli-guides/cli-guides/get-started-with-cli/).
- Netlify's `netlify deploy --allow-anonymous` creates a project and live URL without login, with a one-hour window to claim ownership; Netlify positions this for AI agents and automated workflows — [Netlify CLI](https://docs.netlify.com/api-and-cli-guides/cli-guides/get-started-with-cli/).
- Vercel CLI's `init` initializes example projects locally from its examples repository — [Vercel CLI](https://vercel.com/docs/cli).
- Railway CLI supports `railway deploy --template <name>` and `railway templates search` for published templates — [Railway CLI](https://docs.railway.com/guides/cli).
- Coolify advertises 300+ one-click service templates and provides CLI, API and MCP surfaces for self-hosted deployments — [Coolify docs](https://coolify.io/docs/), [Coolify CLI](https://coolify.io/docs/cli/what-is-the-coolify-cli).
- Netlify recommends pointing agents at the `netlify.toml` JSON Schema and adding `"$schema"` so generated config is validated — [Netlify agent setup](https://docs.netlify.com/build/build-with-ai/netlify-mcp-server/).
- Yoal's roadmap lists "Templates/scaffolding tool for agents" under "Later / maybe"; no template code exists in the repository — [Yoal roadmap](https://github.com/KieranHolroyd/yoal/blob/main/docs/ROADMAP.md).
- Yoal's MCP server includes `create_project` and one-shot `deploy_site`, but no template-aware creation tool — [Yoal design](https://github.com/KieranHolroyd/yoal/blob/main/docs/DESIGN.md).

### Inferences
- **`yoal init` with a small curated template set (small–medium, do first).** Problem: a new user (or agent) has to invent a project layout and a `yoal.json`. Ship 5–8 first-party templates that are guaranteed to deploy: plain HTML, Astro, SvelteKit static, Vite + SPA fallback, Hugo, Eleventy, and a "docs" template. `yoal init [dir] --template astro` writes files, a `yoal.json`, an `AGENTS.md`, and optionally links/creates the project. Keep templates in the repo and version them with the platform.
- **`yoal init --template gh:owner/repo/subdir#ref` (small–medium).** Problem: the most useful template is someone else's repo. Adopt C3's source grammar (GitHub/GitLab/Bitbucket, subdirectory, branch, commit), vendor a tarball, strip `.git`, and run framework detection. This gives long-tail templates without maintaining a registry.
- **Framework detection + output inference (small–medium).** Problem: users must know the output directory and build command. Detect Astro (`dist`), SvelteKit (`build`/`.svelte-kit/output`), Vite (`dist`), Next static export (`out`), Hugo (`public`), Eleventy (`_site`), and static (`public`/root). Print what was detected and allow `yoal.json` overrides. This also improves `yoal deploy` for non-template projects.
- **MCP `list_templates` + `create_project_from_template` (small).** Problem: an agent asked to "make me a landing page" has to scaffold by hand. Add tools that list templates, create a project, write the template files into a workspace path (or return them), and deploy. Reuse the same template manifest as the CLI. This is the clearest "agent-first" differentiator Yoal can ship cheaply.
- **One-click deploy URLs (medium).** Problem: sharing a template with a teammate requires CLI knowledge. Add `/new?template=<id>` (and `/new?template=gh:…`) in the dashboard: sign in, name the project, deploy. A self-hosted install cannot use a central `yoal.new`, but each install can expose its own `/new`. Add a "Deploy this template" badge snippet for READMEs.
- **Agent-oriented scaffolding output (small).** Every `init` should write `AGENTS.md` (project conventions, `yoal deploy`, preview URLs, secret rules, MCP setup) and a `yoal.json` with `$schema`. Cloudflare asks the AGENTS.md question explicitly; Yoal can make it the default. Also write `.mcp.json`/client-specific config or print the exact `yoal setup agent` command.
- **Template gallery in the dashboard (medium, later).** Problem: discovery. A grid with screenshots, framework tags and "deploy" buttons is nice but only pays off once there are many templates and users. Start with CLI + MCP + `/new`.
- **Avoid a hosted template registry / marketplace.** For self-hosted, a registry adds supply-chain and availability risk. Git sources + first-party templates cover the need; sign/verify first-party templates if they are fetched remotely.

### Gaps
- No primary source on Vercel's template catalogue size or one-click deploy flow beyond `vercel init`; the recommendation does not depend on it.
- Netlify's Agent Runners were not separately documented in the fetched page; the `netlify create` behaviour is sourced, but the underlying runner limits/pricing are unknown.
- No data on which frameworks Yoal users actually deploy, so the template list is a reasoned default, not measured demand.
- No source on agent success rates with scaffolded templates; the AGENTS.md/MCP value is inferred from platform investment, not measured.

## Local development (dev proxy for production-like hosts, env sync, tunnel/preview from local machine, local MCP testing)

### Takeaway
"Local dev" now means a proxy that reproduces the production edge: redirects, headers, env vars, framework dev server, and sometimes functions. Netlify Dev is the clearest example (proxy + framework detection + `dev:exec` + context switching); Railway offers `run`/`shell`/`dev`; Cloudflare offers `wrangler dev`. Yoal has no local proxy, so `_redirects`/`_headers` and production host behaviour are only testable after deploy — a sharp pain for a static-first platform.

### Cited Findings
- Netlify Dev runs a local proxy that includes edge logic for custom headers and redirects, environment variables and Netlify Functions, and auto-detects frameworks (Gatsby, Hugo, Eleventy, Next.js and more) to mimic production — [Netlify local development](https://docs.netlify.com/api-and-cli-guides/cli-guides/local-development/).
- Netlify Dev supports `--context production` to run with another deploy context's settings/variables, `netlify dev:exec <cmd>` to run a command inside the environment, configurable `targetPort`/`port`/HTTPS, and a `[dev]` override block with `framework`, `command`, `publish` — [Netlify local development](https://docs.netlify.com/api-and-cli-guides/cli-guides/local-development/).
- Netlify Dev's env behaviour is tied to the `dev`/`all` deploy contexts by default and applies variables to all scopes locally — [Netlify local development](https://docs.netlify.com/api-and-cli-guides/cli-guides/local-development/).
- Railway CLI offers `railway run <cmd>` (run with Railway env vars), `railway shell` (shell with env vars) and `railway dev` (run services locally with Docker) — [Railway CLI](https://docs.railway.com/guides/cli).
- Cloudflare's `wrangler dev` starts a local server for a Worker and is the default inner loop before `wrangler deploy` — [Cloudflare Workers CLI guide](https://developers.cloudflare.com/workers/get-started/guide/).
- Vercel CLI's `dev` replicates the deployment environment locally; `env run -- <command>` runs a command with project env vars; `pull` updates local env/settings — [Vercel CLI](https://vercel.com/docs/cli).
- Yoal serves deployed sites in development at `<slug>.localhost:<port>` and `<slug>--<env>.localhost:<port>` straight from the local object store, so dashboard preview links open real deployed files — [Yoal README](https://github.com/KieranHolroyd/yoal/blob/main/README.md).
- Yoal has no local dev proxy, no env pull, and no tunnel/local-preview command in the CLI surface — [Yoal CLI README](https://github.com/KieranHolroyd/yoal/blob/main/apps/cli/README.md).

### Inferences
- **`yoal dev` (medium, highest local-dev priority).** Problem: `_redirects`, `_headers`, clean URLs and 404 behaviour only work after deploy; developers guess. Implement a local reverse proxy: start/detect the framework dev server (or serve a static dir), apply Yoal's compiled Caddy-equivalent route rules, inject the linked project's env, and print a production-like host (`<slug>.localhost`). Support `--port`, `--target-port`, `--framework`, `--static`, `--context/--environment`, and `--open`.
- **`yoal dev --exec` (small).** Problem: agents/tests need the same env without a long-running server. A one-shot `yoal dev --exec -- <cmd>` (Netlify `dev:exec`, Vercel `env run`) is cheap once env pull exists.
- **`yoal env pull` integrated with dev (small).** Problem: dev and deploy use different secrets. Write `.env.local` only when it does not overwrite uncommitted changes (prompt or `--force`), never print secret values by default, and include a header warning not to commit. This is the most requested local-dev primitive after the proxy.
- **Tunnel / share from local machine (medium–large).** Problem: testing webhooks, OAuth callbacks, MCP clients and mobile devices against a laptop requires a public HTTPS URL. Options: integrate an existing tunnel (Cloudflare Tunnel / `cloudflared`, or a WireGuard path through the agent) and add `yoal dev --tunnel` / `yoal share` that prints a temporary `https://<random>.<content-domain>` URL. Self-hosted makes this attractive: the platform already owns a wildcard cert and edge. Start with `cloudflared` integration (small) before building a proprietary relay (large).
- **Local MCP testing (small–medium).** Problem: agents and MCP client authors cannot exercise Yoal tools offline or against a local control plane without hand-editing config. Add `yoal mcp serve --stdio` (bridge stdio to the remote MCP with the current profile token) and `yoal mcp inspect` (list tools/resources, call a tool, print the JSON-RPC trace). This also makes CI tests of MCP clients possible.
- **`yoal build` local parity (medium).** Problem: "works locally, fails in the builder" due to Node/Bun version, env or build command differences. Add `yoal build` that runs the same builder image/command locally (or in Docker) with `--dry` to print the plan (Netlify `build --dry`). Lower priority than dev; it overlaps with CI logs.
- **Read-only production data proxy (medium, risky).** Problem: reproducing a bug needs production data. A `--prod-data` proxy raises security and privacy issues; prefer a seeded local fixture/template instead. Do not ship a generic production proxy without scoping and audit.
- **Do not build a custom HTTPS CA for local dev.** Netlify documents self-signed cert friction; `<slug>.localhost` over HTTP plus `mkcert` guidance is enough. Yoal's existing `*.localhost` convention is already good.

### Gaps
- No primary source was found on Netlify Dev's live-share/tunnel feature in the fetched page; the tunnel recommendation is therefore an inference from the general need, not a cited parity claim.
- Cloudflare's local dev docs beyond `wrangler dev` (bindings, remote mode) were not fetched; no claim is made about parity there.
- No data on how much time Yoal users lose to redirect/header bugs; the priority is based on the static-first design and the absence of a proxy.
- Local MCP testing has no direct precedent in the surveyed docs; Vercel/Netlify document remote MCP setup, not a local bridge.

### Suggested sequencing across all six areas (for the report writer)

This subsection is cross-cutting; it is placed last so it does not interrupt the key-question structure. If the report needs a single ranked shortlist for "what Yoal should add next", this is the ordering supported by the findings above:

1. **GitHub App + sticky PR comment + commit check/deployment status** — medium, unlocks team review and required checks. (Git)
2. **OpenAPI 3.1 spec + generated TypeScript SDK** — small–medium, unlocks agents, CLI consistency, IaC and docs. (API)
3. **`yoal link` + `yoal env pull` + `yoal logs -f` + `yoal whoami/doctor`** — small each, removes daily friction. (CLI)
4. **`yoal setup agent` / `yoal mcp install` / `yoal agent init`** — small, highest agent-first leverage per engineering day. (CLI/templates)
5. **`yoal dev` local proxy with `_redirects`/`_headers` and env** — medium, fixes the static-first inner loop. (Local dev)
6. **`yoal.json` config-as-code with `plan/apply` and drift exit codes** — medium, reviewable environments without Terraform. (IaC)
7. **Deploy event catalogue + signed webhooks + Slack/Discord** — medium, makes the platform part of the team's workflow. (API/collab)
8. **Templates (`yoal init`, git-source templates, MCP template tool)** — small–medium, cheap on-ramp and agent demo. (Templates)
9. **Per-deployment share links + access requests + release notes** — small–medium each, rounds out collaboration. (Collab)
10. **Terraform provider, GitLab/Bitbucket, in-page comments, screenshot diffs, build cache** — large; sequence after the above based on demand.
